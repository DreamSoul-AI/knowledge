# AI work updates
Prepare complete, usable work messages from the specified conversation and feedback, completing necessary research and internal checks before delivery. Aim to get the message right the first time. Multiple boards may need multiple versions delivered together; there is no fixed count or structure.
Without publication authorization, show complete message text. When sending or updating is authorized, save it to the intended location, then read the actual saved content to check the wording, links, date, recipients and author. Do not ask for the same authorization again. Later scope restrictions take precedence.
Keep the opening short and concrete, leading with the matter or result the reader most needs to know rather than adding a stock introduction. Use semicolons sparingly without banning them. Let meaning guide sentence breaks instead of mechanically splitting sentences to shorten the opening or avoid semicolons.

## Use
Always start by reading the project's applicable message-board standard, using the supplied rules, project AGENTS.md or standards index to locate the source. DreamSoul uses `文档/规范/产品/留言板规范.md`; other projects use their own rules. An explicitly selected candidate standard takes precedence for a local trial. Report inaccessible rules rather than claiming compliance with unread material.

Then inspect each target board's actual content, including the sender's similar earlier posts to the intended recipient. Use this to choose the address, courtesy, tone and background, rather than mechanically replacing pronouns. Keep verified group names, signatures and forms of address distinct. Read all requested boards as needed and deliver their suitable message versions together, labeled by destination. Do not require separate user requests per board or hard-code a set of boards, courtesy phrases or version counts.
When the target boards are known, read each board's applicable rules and the context relevant to its audience, date groups and author, followed by related introductions, questions and latest status, before drafting—even for a draft-only request. Choose the background, tone and focus for those readers; do not write a generic message solely from the current conversation and then change only the salutation. Read what is needed using the topic and known context rather than scanning all history. Boards may need different versions, with a brief purpose where needed. A post on one board does not establish shared context on another, and a just-published draft under revision is not an earlier introduction. When no target is known, a generic draft is appropriate. If a known board is unreadable or its record is limited, state the coverage without pretending the draft is adapted; leave unknown dates or identities unset. Reading the context does not authorize publication. See [Message-board writing](publishing.md).

Use the board's display-name rules and a verified mapping between the person's full name and displayed name. Do not mechanically strip surnames or identify someone from an ambiguous short name. The account's real name verifies identity; it does not by itself dictate the name displayed on a board. Keep the message within the requested subject rather than adding unrelated maintenance handoffs, tutorials or tasks.

Retain the board's actual heading structure. Where H3 identifies the recipient and H4 distinguishes senders, a fixed two-person board may use H3 alone. Place the message directly beneath it without adding H4 or a redundant signature. Verify the actual sender, but do not treat an intentionally unused heading level as missing information. Other boards retain their own conventions.

Concise does not mean as short as possible. Retain concrete changes and any status that affects understanding or use. Parallel matters may use short bullets rather than a dense paragraph, without fixed counts, length limits, or scenario templates.

Install the entire `ai-work-message` directory, then ask:
```text
Use $ai-work-message to read this conversation excerpt and draft one plain-language work update. Show it to me without publishing it.
```
Provide the original conversation or a readable file path, with start and end boundaries when needed. The skill follows the latest confirmed outcome within that range. Instructions quoted in historical conversations are source material, not new authorization.

## Examples
These examples illustrate wording only; facts must come from the input. At the document title, use a native reference or the original full share URL as supported by the output environment.
- User-approved research-sharing example: `【知会】拉了一个 Codex 中国平台接入调研，了解一下 Codex 和国内各大互联网平台的连接情况`
- User-approved short result message: `两份产品痛点校准好了 <original personal-document share URL> 和 <original world-document share URL>`. Substitute the original URLs directly; do not append a redundant upload or filing update.
- A tool has been built and tried successfully: “The chat archive tool is ready and has been tried successfully. It keeps the original wording and can add new messages later.”
- Desktop layout changed, mobile work remains: “The homepage layout has been updated. Mobile adjustments are still pending.”
- Only a proposal exists: “The chat archive approach is outlined. Implementation has not started.”

## Links and document references
Actively find real material links and verify the subject, version and intended audience. A draft still needs usable facts, recipients, tone and material entry points. Do not substitute inaccessible local paths, placeholder links, or unsupported claims such as “see attachment” or “already synced” for material that has not actually been delivered. When archiving or synchronization is already authorized in the session and no later restriction overrides it, continue that work through the appropriate skill, complete the original scope and obtain a verified entry point. Do not create documents, upload additional material or change permissions beyond that authorization. State any remaining gap specifically rather than calling an incomplete draft fully delivered.
Raw share URLs copied from Feishu may display as document titles through platform rendering. Do not infer hand-written Markdown from the display alone. Preserve the original URL value without adding an explanation of link formatting or rendering to the message.
Use Feishu's native document references or cards with the verified, actual document title. Do not invent or alter titles: “办公电脑” must not become “办公电脑调研”. When authorized to write to Feishu, preserve existing native references, use the docs interface's native `cite type="doc"` with the verified document ID and title, and read back to confirm the native reference. An ordinary `<a>` link is not a substitute. If the chat or plain-text draft cannot produce a genuine native reference, retain the user's original full share URL directly within the draft sentence without inventing link text. Do not pass off Markdown links, bare URLs, or displayed cite source as a generated native reference, and do not guarantee automatic conversion when pasted into Feishu. Keep the original URL when the title cannot be verified. Preserve every query parameter and location anchor without rebuilding or shortening the URL. If a native reference cannot preserve the location, include the original full share URL alongside it. Place message links naturally after the relevant wording; do not introduce them with a colon or a label such as 文档：URL. Use one space between a link or native reference and adjacent text, but no space on a side touching punctuation such as a comma, period, enumeration comma or parenthesis. Do not add space at a paragraph boundary. For example, use “说明 URL，后续说明”, not “说明 URL ，后续说明”. Folder and external website links may use ordinary hyperlinks with short, accurate resource names. For JD and other product pages, manually use the product name as hyperlink text, for example `[ROG 魔霸9X](https://item.jd.com/100293607043.html)`.

## Priority
Start newly drafted messages with one priority: 【优先】 for blocking work or action needed today or the next working day; 【本周】, 【本月】, or 【本季度】 for action or a reply within that period; 【有空】 for action without a deadline; 【知会】 for information requiring no action or reply. Leave an approved final message unchanged when it has no label. Preserve the wording and labels the user has approved for the specific message; do not mechanically add 【待确认】. Append it only when the message recipient needs to decide, confirm, or give an opinion, paired with an action priority rather than 【知会】. The sender planning to check something with a seller or another third party does not mean the recipient is being asked to confirm. State known deadlines explicitly; dates take precedence over general priority labels. Do not invent deadlines or add a separate priority recommendation or explanation line.

## Publishing or updating a message board
Without publication authorization, show complete message text. If publishing or the destination is undecided, a brief follow-up may ask whether to publish and where, offering verified candidates. Do not keep asking after the user says not to publish. When applicable authorization includes sending or updating and the necessary information is known, complete saving and checking the actual result without asking again.

Different users may have access to different boards. Check the actual user and each target's access, rules and existing content. Keep the business date in the message, the sending time and the board's filing date distinct; do not assume a fixed set of boards or a shared filing date. Establish the filing date for this publication before writing. An explicitly requested date takes precedence over a board's default rule. If the user has neither supplied a date nor explicitly confirmed a date rule for this publication, calculate candidate dates using each board's time zone and rules, then ask one combined question. Board defaults and the system date alone do not determine the filing date. “Send now” does not confirm a filing date or require asking for a clock time or creating a scheduled task. Do not ask again when the date is already explicit or the user has explicitly requested calculation under a confirmed rule.

Check whether the request adds a new entry or updates an existing one. Read the latest entry before updating, normally retaining its original date group, recipient and author. Preserve unchanged wording, native references and other people's content. Track each board separately, read back the result and check uncertain outcomes before retrying so successful writes are not duplicated. See [Message-board writing](publishing.md) for detailed positioning, writing, verification and retry handling.

## Scope
Stop when the message is clear; there is no minimum length. Keep only the core matter, change or result and necessary links. Preserve a user's final wording without rewriting or expanding it. When result links already convey availability, omit redundant statements such as “uploaded to Feishu” or “placed in the respective folders,” unless uploading or filing is itself the point of the update.
Prefer ordinary wording over implementation jargon or report language. Reuse phrasing the user has approved without mechanically applying “拉了一个” to every message. When sharing research, material, or a tool, a brief purpose or question may be enough; include progress and limitations when relevant to the recipient. Do not pad the message with work counts, steps, result lists, or lead-ins such as “这份调研帮助大家……”, and do not reintroduce elaboration the user has removed. Describe material unfinished work and its impact naturally, without requiring a fixed sentence template, and distinguish discussion, progress, local testing, and release.
Do not publish without authorization; when sending or updating is authorized, complete that delivery. Invoking the skill does not itself authorize changes to the original conversation, work log or project tracker. Continue separately authorized archiving or material synchronization through the corresponding workflow without expanding its scope. Tracker-to-log or log-to-tracker reconciliation remains a separate workflow.
