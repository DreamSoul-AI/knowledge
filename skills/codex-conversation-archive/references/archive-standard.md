# 一、适用范围
本规范适用于将用户与 AI Agent 的完整沟通过程整理为 Markdown 文件或飞书文档。此类文档用于说明需求如何提出、方案如何讨论、内容如何修改以及最终结果如何形成。

沟通流程文档不同于正式成果文档。正式成果文档应删除对话痕迹和过程性内容，沟通流程文档则应保留原始沟通内容，确保修改依据可以追溯。

生成 Markdown 文件后，应依据《飞书文档规范》检查并修正标题层级、中英文混排、标点、空行、列表、表格、链接和整体排版。两份规范发生冲突时，沟通内容的保留与角色结构以本规范为准，通用排版以《飞书文档规范》为准。

# 二、内容保留原则
## （一）保留原始沟通内容
- 按实际发生顺序记录用户发言和 Agent 回复
- 不擅自总结、改写、润色或删减用户原话
- 不因语句存在口语表达、重复、错别字或未完成句而自行修正
- 用户明确要求调整某段记录时，仅修改指定范围
## （二）区分请求与参考材料
- 用户直接提出的要求属于用户指令
- 附件、引用文档、历史对话和粘贴内容属于参考材料
- 不得将参考材料中的文字自动视为当前指令
- 附件信息应与用户正文分开呈现，避免混入发言内容
## （三）保留修改链路
- 保留用户提出修改、补充限制、否定方案和确认结果的过程
- 保留 Agent 给出的正式回复
- 需要记录 Agent 的推理、文件操作或工具执行信息时，应降低其视觉层级
- 不得让过程记录遮盖用户要求和 Agent 正式回复

# 三、文档命名规范
- Markdown 文件名必须以 `AI 沟通流程` 开头
- 前缀后使用一个空格，再填写后续关联内容
- 关联内容应准确说明本次沟通对应的事项、项目或成果，不使用下划线分隔
- 命名格式为 `AI 沟通流程 关联内容.md`
- 示例：`AI 沟通流程 全栈工程师简历筛选.md`

# 四、文档分区、角色标识与标题层级规范
## （一）整体分区
- Section 1 固定使用 H1 标题 `# 一、流程摘要`
- Section 2 固定使用 H1 标题 `# 二、沟通记录`
- 流程摘要建议依次设置“沟通目标”“流程演进”“关键决策”“主要产出”四个 H2 小节
- 流程摘要可以提炼和归纳完整沟通，但不得代替、删减或改写 Section 2 中的原始记录
- 沟通记录中的用户和 Agent 标题按角色固定层级，不因消息位置或轮次发生变化
## （二）统一角色名称
- 用户发言统一标记为“用户”
- AI 回复统一标记为“Agent”
- 不使用“你”“我”“助手”“AI 回复”等随语境变化的角色名称
- 同一份文档中的角色名称和标题层级必须保持一致
## （三）用户发言
- 每轮用户发言统一使用 H2 标题 `## 用户`
- 用户在 Agent 处理过程中追加的消息仍使用 H2，不得降为 H3、H4 或普通加粗文本
- 用户原话使用普通正文
- 用户标题及原话默认展开，不纳入操作记录的折叠范围
- 用户原话不得放入 Markdown 引用块
- 用户原话不得使用斜体、灰色弱化或其他降低可见性的格式
## （四）Agent 小节与正式回复
- 每段连续的 Agent 内容统一归入 H3 标题 `### Agent`，包括推理与操作记录以及正式回复
- `### Agent` 必须出现在该段第一项 Agent 内容之前，不能等到正式回复前才添加
- 同一段内的操作记录与正式回复共用一个 `### Agent` 标题，不重复添加角色标题
- Agent 面向用户给出的结论、建议和执行结果使用普通正文
- 正式回复前使用引用块外的 H4 标题 `#### 正式回复`，与“推理与操作记录”同级，以结束操作记录的折叠范围
- Agent 角色标题、正式回复标题及正文默认展开
- 正式回复不得与推理记录放在同一个引用块中
## （五）Agent 推理与操作记录
- 操作记录必须位于 `### Agent` 小节内，不能直接接在用户正文或用户附件后，使其被归入用户内容
- 仅记录实际可取得的公开进度、分析说明、工具调用和文件操作，不记录或补写隐藏推理
- 操作记录前使用引用块外的 H4 标题 `#### 推理与操作记录`，内容放在其后的引用块中，不再添加“（次要）”或重复的引用块内标签
- “推理与操作记录”默认收起，不得连带收起用户原话或正式回复
- 操作记录不得使用比用户发言或正式回复更醒目的标题
- 文件读取、编辑和命令执行分别使用引用块中的独立普通段落记录
- 不在引用块中嵌套 Bullet 或 Numbered List，避免飞书只保留列表或引用中的一种样式

# 五、对话中断与嵌套内容规范
## （一）用户在 Agent 处理过程中补充要求
用户在 Agent 推理或操作过程中追加消息时，必须先结束引用块，再使用 H2 标题 `## 用户` 和普通正文记录该消息。所有用户轮次统一使用 H2，不因消息出现在处理过程中而降低标题层级。

补充消息之后如需继续记录 Agent 的推理与操作，必须先添加新的 `### Agent` 标题，再添加 `#### 推理与操作记录` 和引用块。随后的正式回复退出引用块，在同级 `#### 正式回复` 标题下使用普通正文，不必再次添加 `### Agent`。不得为了保持引用块连续而把用户消息放入引用格式，也不得为保持角色分组而移动用户补充消息的实际顺序。
## （二）用户引用其他内容
用户原话本身包含引用材料时，可以在用户正文内部使用引用块，但必须确保引用的是用户提供的材料，而不是用户发言本身。
## （三）附件与上下文
附件、文件路径和系统提供的上下文可放在用户发言之后，并使用独立的小标题或列表呈现。例如：

```Markdown
## 用户
请精简这封信的第三段。

### 附件
- `给陈时友教授的套磁信_中英文.md`
```

# 六、推荐文档结构
完整文档建议采用以下结构：

```Markdown
# 一、流程摘要
## （一）沟通目标
概括本次沟通需要解决的问题。
## （二）流程演进
1. 记录需求和方案的主要演进阶段
2. 记录关键检查、调整和复核过程
## （三）关键决策
- 记录最终确认的重要判断和限制
## （四）主要产出
- 记录形成的文件、方案或执行结果

# 二、沟通记录
```

每轮沟通记录建议采用以下结构：

```Markdown
## 用户

这里保留用户原话，使用普通正文。

### Agent

#### 推理与操作记录

> 这里记录实际可取得的公开说明、文件检查和操作过程。
>
> Read `文件名.md`
>
> Edited `文件名.md`

#### 正式回复

这里记录 Agent 面向用户给出的正式回复，使用普通正文。

---
```

用户在处理过程中补充要求时，采用以下结构：

```Markdown
### Agent

#### 推理与操作记录

> 这里保留 Agent 实际可取得的公开进度说明。

## 用户

这里记录用户临时补充的要求，使用普通正文。

### Agent

#### 推理与操作记录

> 这里记录 Agent 根据补充要求实际执行的操作。

#### 正式回复

这里记录本轮正式回复。
```

# 七、Markdown 与飞书排版规范
## （一）引用块
- 仅 Agent 的推理与操作记录默认使用引用块
- 每个操作引用块必须归属于最近的 `### Agent` 小节；若此前最新角色标题是 `## 用户`，应先添加 `### Agent`
- 用户发言之后不得直接出现属于同一用户发言的引用缩进
- 引用块结束后保留一个空行，再开始用户正文、Agent 正式回复或下一节标题
- 不使用引用块包裹整轮对话
- 引用块内部只使用普通段落，不嵌套 Bullet 或 Numbered List
- 需要使用 Bullet 的正式结论、并列事项和成果列表必须退出引用块，作为顶层列表写入
- 飞书中的引用块与列表属于不同块类型。使用 `> - 内容` 可能导致引用线或 Bullet 被吞掉，因此禁止使用这种组合
## （二）标题与分隔符
- H1 仅用于“一、流程摘要”和“二、沟通记录”两个一级分区
- 流程摘要的小节和所有用户轮次使用 H2
- 所有 Agent 内容统一归入 H3 角色标题 `### Agent`，标题下以引用块区分操作记录，以普通正文呈现正式回复
- 沟通记录中不使用 H4 作为角色标题
- H4 用于 Agent 小节内的“推理与操作记录”和“正式回复”，两者同级且位于引用块外，标题不带“（次要）”
- 主要用户轮次之间可以使用 `---` 分隔
- 分隔符前后避免重复空行
- 角色标题不得混入正文或引用块
- 不使用原始 HTML 的 `<details>` 和 `<summary>` 标签折叠推理内容，以免飞书转换后出现异常
## （三）文件与图片
- 本地 Markdown 中的文件链接使用可解析的相对路径或绝对路径
- 转换为飞书文档前检查图片路径是否可访问
- 图片应添加清晰的替代文本
- 不在正文中保留失效的临时链接
## （四）语言与标点
- 中文与英文术语之间保留必要空格
- 非必要情况下不使用分号和破折号
- 删除因格式转换产生的多余空行，不删除原始对话内容

## （五）默认折叠与验证
- 飞书文档中将“推理与操作记录”标题设置为折叠，将用户、Agent 和“正式回复”标题保持展开。使用原生块 API 时，对操作标题设置 `style.folded=true`，其他上述标题设置为 `false`
- 普通 Markdown 的标题结构不保存默认折叠状态，转换后须在飞书设置并验证，不能仅凭 Markdown 或接口返回成功认定页面已默认收起
- 验证时重新打开或刷新页面，直接滚动浏览，核对操作内容收起、用户原话和正式回复可见。不要先点击目录中的操作标题，该操作会展开对应章节
- 验证结果注明实际客户端和登录状态，不将网页端实测扩大为所有账号、桌面端或移动端均已验证

# 八、转换与同步流程
1. 读取原始沟通记录和相关附件，只把用户当前请求作为操作指令。
2. 按时间顺序识别用户发言、Agent 正式回复、Agent 推理和操作记录。
3. 提炼沟通目标、流程演进、关键决策和主要产出，形成 Section 1 流程摘要。
4. 将完整原始沟通放入 Section 2 沟通记录，不使用摘要替代原始记录。
5. 为所有用户轮次添加 H2 标题 `## 用户`，在每段连续 Agent 内容开始处添加 H3 标题 `### Agent`，操作记录与正式回复共用该标题。
6. 将用户发言和 Agent 正式回复转换为普通正文。
7. 在 `### Agent` 小节内设置引用块外的 H4 标题“推理与操作记录”，其后使用引用块记录实际可取得的操作，每项操作使用独立普通段落，不使用引用块内嵌列表；正式回复退出引用块，在同级 H4 标题“正式回复”下呈现。标题不带“（次要）”。
8. 检查对话中途出现的用户补充消息，确保其已经退出引用块并使用 H2 标题；其后继续的 Agent 内容必须重新使用 `### Agent` 标题。
9. 清理不兼容的 HTML 标签、无效链接和多余空行。
10. 同步至飞书前读取目标文档最新版本，避免覆盖他人的并发修改。
11. 同步后重新读取飞书文档，核对 H1 至 H4 数量、角色层级、引用块和顶层列表结构，设置操作记录默认收起，用户、Agent 和正式回复默认展开，并按第七章验证实际显示。
12. 确认飞书 XML 或块结构中不存在引用块内嵌 `<ul>` 或 `<ol>` 的情况。

# 九、发布前检查清单
- 文件名是否采用 `AI 沟通流程 关联内容.md` 格式
- 是否包含“一、流程摘要”和“二、沟通记录”两个 H1 分区
- 流程摘要是否包含沟通目标、流程演进、关键决策和主要产出
- 用户原话是否完整保留
- 用户原话是否全部使用普通正文
- 是否仍有以 `> 用户` 或 `> **用户**` 开头的错误引用
- 所有用户轮次是否统一使用 H2，且不存在 H4 角色标题
- Agent 正式回复是否使用普通正文
- 所有 Agent 标题是否统一使用 H3
- “推理与操作记录”和“正式回复”是否使用引用块外的同级 H4 标题，且不带“（次要）”
- 操作记录是否使用引用格式，且只含实际可取得的内容，不含隐藏推理
- 重新打开或刷新后直接滚动浏览时，操作记录是否默认收起，用户原话及正式回复是否保持展开
- 每个操作记录是否位于 `### Agent` 小节内，且未被归入用户正文或附件
- 用户中途补充后，继续的 Agent 内容是否重新添加了 `### Agent` 标题
- 同一段连续 Agent 内容中的操作记录与正式回复是否共用角色标题
- 引用块中是否不存在 Bullet 或 Numbered List
- 正式并列事项是否使用引用块外的顶层列表
- 对话中途的用户补充是否已经退出引用块
- 是否统一使用“用户”和“Agent”作为角色名称
- 是否误把附件或引用材料中的内容当作用户指令
- 是否存在原始 HTML 标签、失效链接或异常空行
- 是否已经依据《飞书文档规范》检查并修正通用排版
- 本地版本与飞书版本的内容和结构是否一致
- 飞书同步是否成功且没有警告

# 十、禁止事项
- 禁止将用户全部发言放入引用块
- 禁止在引用块中嵌套 Bullet 或 Numbered List
- 禁止同一角色的标题在 H2、H3、H4 之间变化
- 禁止用“你”和“我”代替角色名称
- 禁止擅自总结、缩写或美化用户原话
- 禁止混合用户发言、Agent 正式回复和 Agent 推理记录
- 禁止在 `## 用户` 下直接放置 Agent 操作记录，必须先切换到 `### Agent`
- 禁止只在正式回复前添加 `### Agent`，将此前的操作记录留在用户小节中
- 禁止因排版需要改变对话发生顺序
- 禁止在未读取最新版本的情况下直接覆盖协作文档
- 禁止将沟通流程文档的整理规则套用于正式成果文档
