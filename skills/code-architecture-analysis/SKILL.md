# 代码架构分析 Code Architecture Analysis

回答一个能核对的架构问题。已有分析文档时，把待复查的结论当作待证主张，用源码和原始运行记录重新判断。分析多个场景时，先走通对用户结论影响最大的一条路径。

## 定位分析对象

- 读取项目入口、适用的代码架构分析规范及已有成果。记录仓库、提交或工作区差异、入口、目标场景和运行条件。优先从固定提交读源码，附上实际采用的配置。分析本地未提交实现时，指出影响结论的改动。
- 输出分析文档前，沿当前 `AGENTS.md` 读取 `USER.md` 中的默认文档规范和场景偏好，结合本次要求及仓库约定选定格式，并读取规范正文。本地 Markdown 预览也从起稿时采用选定规范。DreamSoul 的《飞书文档规范》可从资料库 `AGENTS.md` 定位。
- 先写下要解释的现象或可核对的主张，例如「提交导入请求返回后，处理在哪执行，什么时候才算完成」。已有性能、可靠性或架构结论时，明确它说的是默认行为、特定环境还是普遍行为。按所需直接读源码、配置、测试、日志和回执。

## 走通机制

- 从调用方实际使用的公开入口和组件装配开始，定位调用者、运行对象的选择条件、实现及返回路径。跨线程、进程或服务时，指出交接的对象和触发条件，以及谁负责保存、取消、重试或报错。按当前问题走通正常路径及会改变结论的异常。
- 跟踪决定结果的数据或状态，看它在哪里创建、传递、改变和持久化，明确哪个模块持有状态、哪些调用方读写它。区分声明、默认配置、实际生效配置及运行观测。动态分派和可选配置追到注册、选中和调用点。给关键跳转附同一版本的文件、符号或行号。
- 结论依赖某个执行边界时，选一个能改变结论的反例。可安全复现时优先复用项目的隔离测试，同时检查返回结果和输入前后的实际状态，例如预检被拦和已开始写入后的中断。
- 涉及异步或并发时，区分线程、进程和设备各自的执行边界。沿代表路径推演谁提交、何时可读、谁在哪一步等待，以及失败、取消或一直不返回时由谁通知和收尾。结合任务需要比较相关方案对正确性、等待时间和资源占用的影响。实测与条件性判断分别标明。

## 给出可复查的判断

- 对每条关键主张说明证据到底支持什么。源码闭合时写明适用条件。使用旧实测时核对版本、输入、环境、对照及原始回执，区分已有实测与本轮新跑。运行现象的归因需要能区分主要解释的证据。缺少关键一跳时，收窄结论并指出哪条日志、配置或测试可以补证。
- 核对单个问题时，先给出判断，再解释一条从入口到结果的路径。读者应能按证据复核输入、执行位置、状态及结果。若对照支持「可导致」但没有证明现场原因，就把两者各自说清。架构建议沿用项目设计、开发和验收流程。
- 给 Agent 做巡检时，从项目已确认的架构约束或本次指定的质量目标取检查项。每项说明什么表现算符合要求、沿哪条路径检查、实际证据是什么。给出「符合」「发现偏差」或「证据不足」及理由。发现偏差时写明影响和复核方式，代码修复和定时运行按另行确认的范围执行。

## 整体分析的通用大纲

分析整个系统或一个子系统时，按以下顺序组织正文。分析目标和证据决定各章的展开深度。 所有图只保留关键对象和关系，节点与箭头用短标签，条件和原因放在图旁正文。

1. **总体架构**。把可编辑的 Mermaid 总图紧接文档标题或首节标题，标明系统边界及箭头含义。图后用简短文字交代项目定位、核心功能和技术实现，再给一个快速开始示例
   - **概述**。说清项目是什么、解决什么问题、一次使用会得到什么结果。「技术实现」用短项目符号列表交代技术栈、主要模块及连接方式，每条讲清一个机制如何支撑功能
   - **快速开始**。参考项目 README、示例或测试，给出调用方实际使用的最小场景。写清输入、操作和可观察结果，注明依赖条件，并把关键步骤链接到相应的公开入口和实现
2. **职责边界**。沿实际交接顺序用正文讲清各组件的分工。每段说明一次交接，明确调用方、交付对象及持有、读写和清理责任。如需表格，只用短语对照同口径信息
3. **架构设计**。逐个展开主要组件内部怎样组织、遵循哪些约束、关键选择怎样影响调用与恢复。用源码例子说明输入如何变成状态或结果。整体分析至少用一张可编辑的内部结构图或状态图表达关键设计，按需用短表对照状态、存放位置或取舍。说明设计原因的直接依据，推断标为分析判断。需要展开代码结构时，映射到源码模块、公开入口和依赖方向
4. **运行路径**。选一个代表场景，用可编辑时序图或流程图展现关键交接，再解释触发条件、调用、数据和状态如何变化。从图中可定位的交接点接出失败路径，说明错误如何传播、什么状态会留下、由谁收尾
5. **专项分析**。把影响理解或判断的项目特有问题作为小节展开，例如并发、阻塞、持久化或部署差异。适用时说明当前技术选择的条件与代价。范围简单时可省略本章
6. **验证依据**。交代源码版本、运行条件和证据范围，区分源码观察、实测和仍待验证的判断。关键依据留在正文附近，末节集中说明验证范围并给出复查入口

交付前按读者顺序复查。只读开篇就应能说清项目用途、技术连接方式，并能从快速开始示例找到实际代码。确认设计章解释关键模块的内部机制，运行图和正文能互相定位正常与失败交接，关键解释有源码或实测依据。核对职责边界的正文是否讲清交接，技术实现是否便于扫读，图中是否只留下关键关系。检查标题、链接和可用的图形渲染。

例如，`用 $code-architecture-analysis 核对这份架构报告中的导入完成判断，沿固定版本找到源码、结果写入点和已有运行证据。`
