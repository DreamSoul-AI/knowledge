# 工作总结 work-summary

先整理完整工作情况，供本人判断哪些已收尾、哪些仍需处理。总结可独立用于回顾和交接，也可交给工作留言筛选分享内容。

## 确认范围

接受指定任务、对话、原始材料，以及可选的补充材料和适用要求。先读取当前项目适用的文档规范，本地 Markdown 也按其组织。资料缺失时说明实际覆盖范围，继续可独立完成的部分。

每次新启动跨对话全局盘点，先请用户确认具体起止日期、时间、时区和来源范围。可查找上次成功汇总或发布位置作为候选起点，不能自动采用。确认前可准备来源清单，确认后再读取窗口内正文。沿用同轮已确认范围继续校准时不反复问；扩大或重开范围再确认。指定单项任务的总结不强制增加全局日期确认。

## 盘点和核对

跨对话读取按[来源收集](references/collecting.md)处理分页、时间边界、证据和缺口。单项任务直接使用指定来源，避免无关扫描。

按实际事项归并协调、执行和验证等对话，避免将同一交付重复计数。区分讨论、计划、实现、测试、提交、发布、安装和业务交付；结论回到原始要求、正式回复及可取得的产物核对，不凭标题、完成标签或修改时间认定收尾。某个产物已完成不等于整个项目完成。

交付前对照已取得来源，检查有效成果、独立阶段结果和关键未完项是否呈现；项目整体未完成不能掩盖已经完成的独立成果。归并、排除或压缩时保留判断所需事实。用户举例指出遗漏后，检查同类问题，仍按总结目标组织全文，不把举例顺序当作章节顺序或优先级。

固定截止点，说明当时完成了什么、还缺什么。截止后的成果不回填为当时已完成；无法核实的状态明确保留待核，不补写推测事实。

## 交付工作总结

先用简短总览说明整体进展和主要未收尾项，再按读者实际工作结构组织；多部门材料可采用“部门 → 项目”，在项目内呈现成果、未完与待核状态，不把同一项目拆散到多个状态大类。单项目或简单回顾无需凑部门层级，无内容的分组省略。每项讲清成果或变化、必要依据和入口、剩余工作，以及需要本人处理的事情。正文用短段落或分层 bullet 便于扫读，表格只用于简短比较。

保留范围内的全部有效工作，包括未完成、私人或暂不适合分享的事项。不要按是否值得发布提前删减事实，也不强制每项都有行动。已有材料保留真实入口；内部来源和本地路径可作为本人核对依据，但不能当作已交付给外部读者的公共链接。说明未覆盖来源及其影响，不把部分读取说成全部盘点。

## 保存和接续

保存工作总结时，在 `工作总结/作者姓名/` 下直接保存 `工作总结 日期.md`，不再套日期目录，飞书文档名对应为“工作总结 日期”。日期采用本次明确指定的工作归属日期，否则按适用的本人日期规则和任务上下文确定，不直接取生成日。作者采用当前 `USER.md` 或本次明确指定的真名，不用 GitHub username、机器用户名或留言署名代替。读取[归档参考](references/archiving.md)，定位本地和云端各自的工作总结根入口，关联本轮材料。同轮接续沿用原稿，分别记录工作归属日期、实际覆盖范围和最近更新时间，不因跨日更新另建总结。

先核对现有成果和在用状态。新建总结可直接按该结构保存；既有总结的移动要按本次范围处理，并同步修复相对引用和已有映射。不为采用目录约定自动迁移历史材料、创建飞书目录或上传。

## 交给下游使用

需要工作留言时，将完整总结及时间范围、截止点、状态依据和材料入口交给 `work-message`，由它校准分享事项、受众并逐板成文。接口使用普通正文、Markdown 文件或可读链接，不要求固定 JSON 或额外服务。下游复用同轮范围和有效证据，只补查缺口或变化，不重复全部扫描。

总结完成、已发布过什么、建议分享什么分别判断。本技能不自行选择通报对象或发布留言，不上传对话原文，也不改日志和总表；这些操作需要对应流程及实际授权。
