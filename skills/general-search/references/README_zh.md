# 通用调研规范 General Research Standard

[English](README.md) · [General Search Skill](../SKILL.md)

在 Codex 中调用 `$general-search`，提供课题、想回答的问题及已有材料。正式调研先写大纲，再写对应正文。以下是可直接使用的规范正文。

## 一、适用范围与核心原则
制定日期：2026年9月14日。适用于研发相关的非学术资料收集、技术理解、整理分析和调研报告写作。

写大纲前，从项目入口找到并阅读适用的文档规范正文，例如项目采用的《飞书文档规范》。即使先写本地 Markdown，也按适用条款确定大纲、正文和来源索引的命名、标题层级、排版、表格和图文格式，并在交付前按同一规范核对。项目没有适用规范时，采用本指南。上传或转换时再核对目标平台的实际显示。

本规范用于回答：一个技术或工具是什么、如何工作、解决什么问题、有哪些实现和使用边界，以及在给定场景下可以怎样使用。适用课题包括软件与开发工具、框架与平台、系统内部机制、协议与接口、工程流程、技术生态、软硬件方案及相关资料整理。

“非学术”表示以实际技术、系统和工程问题为重心。参考资料可以是官方文档、源码、标准、技术文章、产品资料、讨论记录、内部记录，也可以包含论文。不要求以论文为中心，不使用发表渠道排名衡量通用资料价值。

调研可以只形成可靠的知识梳理，不必给出采购推荐、实施方案或实验结果。学术问题、论文贡献与研究脉络为主的任务使用《文献调研规范 Literature Search Standard》。混合课题按问题分工，互相引用，避免重复维护同一份资料。

用户要求分别交付，或实践与学术问题均需独立展开时，在同一课题下分别形成通用调研与文献调研正文。通用调研解释实际使用、管理整理、平台差异、操作流程及持续维护，文献调研解释研究脉络、方法机制和论文证据。共用来源的元数据只维护一处，实践分析不能只作为文献调研的来源附件；不要求所有课题一律交付两套报告。

核心原则：

- **问题先于资料**：先明确要回答什么，再决定查哪些来源和写到什么深度
- **解释先于罗列**：说明机制、关系、条件和代价，不能只堆术语、链接和功能清单
- **证据对应结论**：关键事实附近有引用，引用能定位到实际支撑内容
- **区分事实与判断**：来源陈述、源码分析、本地实测、推断和建议不能混写为同一种事实
- **保留适用条件**：版本、平台、配置、时间和场景是技术结论的一部分
- **承认未知**：未查到不等于不存在，未验证不等于不支持，资料矛盾不能强行消除
- **按需交付**：正式调研先做大纲，再交付正文。小课题的大纲可短，索引与附件按需要另建
- **能复查、能续用**：读者能找到依据，理解分析过程，并知道后续需要确认什么

本文的“必须”是最低交付要求。“建议”可按规模裁剪。“按需”只在对应任务适用时采用。裁剪不免除来源追溯、范围说明和事实准确性要求。

指定材料或规范无法读取时，记录路径失效、工具缺失、认证、资源权限或正文不完整等实际原因，以及已读范围和受影响的结论。先尝试同一资料的已知可用入口，继续不依赖缺失项的工作。关键依据仍缺失时，将相应判断保留为待核，并列出需要补齐的资料。

## 二、启动调研：明确问题、范围和深度
### （一）最小任务定义
开始前在大纲或报告开头写清以下信息。可从已有任务与项目资料中提取。缺失信息影响结论时明确标记，不自行补成项目事实。

| **项目** | **需要说明的内容** |
|---|---|
| 目的与读者 | 为谁整理，解决什么理解问题或支持什么决定 |
| 核心问题 | 可以逐项回答的问题，而不只是一个领域名称 |
| 研究对象与边界 | 纳入哪些系统、技术和场景，哪些暂不展开 |
| 已知约束 | 与任务有关的平台、现有架构、设备、预算、人员或兼容要求。不适用可省略 |
| 信息时间 | 信息截止日。涉及动态资料时另记实际访问日 |
| 深度与产物 | 概览、机制分析、方案比较或验证。需要哪些交付文件 |

问题应具体。例如，将“调研操作系统”收敛为“比较三个系统中文件读取的组件、状态、完成路径及差异”。将“调研 CI/CD”拆为集成验证、构建、发布和追溯等问题。

### （二）选择调研重心
| **重心** | **主要回答** | **合适的结果** |
|---|---|---|
| 资料梳理与知识概览 | 有哪些概念、对象、资料入口，彼此如何关联 | 分类地图、关键解释、阅读路线 |
| 机制与实现研究 | 谁执行、状态在哪里、如何协作、为何这样设计 | 架构与执行路径、源码定位、边界分析 |
| 工具与方案比较 | 在相同需求下，各方案能力和代价有何差异 | 比较矩阵、适用条件。需要决策时给建议 |
| 工程实践研究 | 某种流程如何解决问题，落地有哪些前提 | 实践机制、项目映射、待验证事项 |
| 问题定位与验证 | 哪种解释与现象一致，如何排除其他原因 | 证据链、验证记录、结论边界 |

一个课题可以组合多个重心，但应有主线。不为凑齐模板而强加时间线、竞品榜单、代码示例或部署步骤。

### （三）交付规模
先由 Agent 根据用户用途、问题跨度、对象或路线规模，以及关键机制和证据所需覆盖判断规模，不默认小课题，也不默认要求用户选大小。体系、架构或技术路线等正式课题先覆盖主要类别与代表实际实现，再安排机制解释和比较。分阶段可以改变研究顺序，不缩减总范围，先前的小实验不自动限定后续正式调研。只有明确局部或实际范围确实有限的查询才轻量交付，不以篇幅、标题数量或引用数量代替覆盖判断，也不反向要求每次写长报告。

- **小型课题**：先写简要大纲，再写包含范围、核心回答、局限和 References 的报告。来源信息直接放在文末。明确只交一份短稿时，把简纲放在同一文件
- **综合课题**：先写独立大纲，再完成对应的正式报告。资料较多或反复引用时增加独立来源索引
- **长期课题**：在上述基础上，按需增加检索日志、资料附件和结构化记录，便于持续更新或交接

大纲应写明各章标题、要回答的问题、预期证据和待确认内容，并规划文字解释、Mermaid 图示与适用的 LaTeX 公式如何共同说明核心概念。参考资料应作为独立部分规划，列出已有研究、代表系统和协议等资料组、拟重点阅读的材料及其与正文问题的关系。检索后允许调整分类与章节，最终大纲和报告应对应。

**大纲层级**。综合课题的大纲必须呈现与正文对应的实际标题树。按主题从属关系逐级组织标题：一级章节使用 H1，具有多个实质子主题的章节展开为 H2，子主题内部仍有独立问题时继续使用 H3 或更深层级，层级保持连续。简短且主题单一的章节可保留一级标题，小节数量与深度按实际问题确定。

**小节内容**。大纲中的实质小节应交代本节回答什么、采用哪些代表材料或证据、与相邻小节怎样分工，存在关键未知时另列待核实项。按内容选用简短段落或条目，任务元信息、参考资料规划与正文目录分别组织。标题格式采用目标交付环境和适用文档规范。

### （四）分类与分析轴
章节和资料分类选择一个稳定主轴，例如技术机制、系统组件或待解决的问题。同级类别按同一维度划分，例如按技术机制分为“缓存机制”“调度机制”，厂商、年份和阅读状态可作为比较字段。

对象、平台、应用场景、版本和证据类型可用独立章节、比较表或标签表达。一个对象跨多个主题时，用交叉引用连接。不要在每章重复介绍全文背景。确需按不同产品或系统展开时，各部分尽量围绕共同问题比较，并说明覆盖差异。

大纲应注明每章采用的分类轴、代表系统或资料，以及与其他章节的分工。分类是帮助理解的分析工具，不应被表述为唯一或官方分类，除非有相应依据。

## 三、资料检索、筛选与记录
### （一）检索流程
1. **检查已有资料**：阅读相关调研、项目约束和既有规范，区分可复用的认识与需要重新核验的事实。
2. **规划首稿覆盖**：按核心问题列出主要方案、共同场景、关键对照、适用条件和可能改变判断的反例，再整理检索词。更新旧稿时，把仍有效的证据和方法纳入本次大纲。
3. **建立主来源**：优先找到官方文档、规范、公开仓库或原始发布记录，再按问题追查细节。
4. **横向补全**：查替代实现、限制、失败案例、兼容说明和反对证据，避免只沿一个产品的介绍展开。
5. **纵向追溯**：必要时从教程追到接口文档、源码、设计讨论和变更记录，确认说法实际来自哪里。
6. **成稿前核对证据**：按大纲核对核心问题和主要分支，用直接证据完成比较，再撰写第一稿。检索发现新路线时，同步调整大纲和正文。

搜索结果摘要、聚合页面和 AI 生成内容可用于发现线索，不能替代关键事实的原始依据。引用前必须查看实际支撑内容。只读了摘要、部分章节或转引资料，应如实说明，不能声称阅读全文或完成源码验证。

### （二）按用途评价来源
| **来源类型** | **适合支撑** | **需要注意** |
|---|---|---|
| 官方技术文档、接口文档、标准 | 定义、约定、公开能力和兼容边界 | 确认版本、规范状态。设计约定不等于每个实现都符合 |
| 官方源码、测试、发布与变更记录 | 特定版本的实现、修复和演进 | 固定 tag/commit。某段代码存在不代表默认路径会执行 |
| 官方产品页、价格页、许可文本 | 厂商声明、功能范围、计费与许可条件 | 区分营销描述和技术保证。记录版本、地区、计划和日期 |
| 原作者文章、设计文档、工程分享 | 设计理由、经验和取舍 | 明确作者场景，不能自动推广到所有系统 |
| Issue、讨论区、问答与用户案例 | 故障线索、边界情况和实际体验 | 核对版本、复现条件、维护者回应和解决状态 |
| 第三方教程、评测和综述 | 入门、横向比较、独立观察 | 核对方法、利益关系和原始出处。排除转载形成的假交叉验证 |
| 内部文档、日志和本地实测 | 项目约束、特定环境的实际行为 | 标明环境、日期与可追溯记录。经验不能冒充通用保证 |
| 学术论文与技术报告 | 原理、历史来源、方法和实验依据 | 区分研究结果与当前产品已经实现的能力 |

不设通用的 A/B/C 质量总榜，也不把“官方”理解为所有结论都正确。判断来源是否适合当前主张，看直接性、具体程度、版本匹配、可复核性和潜在偏差。

### （三）采纳、排除与停止条件
- 与核心问题直接相关、能支撑事实或解释差异的资料进入正文证据或来源索引
- 只有背景价值的资料可列为延伸阅读。重复转载优先保留原始出处
- 排除明显版本错配、无来源的关键数字和与任务无关的内容。影响结论的排除项记录原因。不要求记录每个无关搜索结果
- 关键且有争议的结论应寻找独立证据。多个网站转述同一公告不算多份独立证据。同一厂商的文档与源码可以互补，但不代表独立评测
- 正式调研在同一任务内完成检索、分析、成稿和自查，一次交付完整报告。按大纲逐个核对核心问题和主要分支，用直接证据在正文充分展开代表方案的机制、实现差异、适用条件、代价和失败场景，围绕共同场景比较。表格用于速览，判断依据和关键反例在正文讲清
- 交付前复核覆盖和证据。若仍发现会改变结论或选型的遗漏，定向补证并同步修正摘要、对照和结论。查证到可用证据的边界后，把仍无法确认的事项、已查范围和对结论的影响写入同一份正式报告
- 不按固定篇数、字数或搜索次数验收，不声称完成穷尽检索，除非确有相应方法和记录

大型或长期课题的检索日志至少记录：日期、问题或查询、重要来源、采纳或排除原因、未解决事项。日志记录研究路径，不需要倾倒全部工具输出。

### （四）阅读深度与资料价值
阅读深度按资料与课题的相关性确定。对支撑核心结论、存在争议或需要解释实现的材料深入阅读。

| **阅读状态** | **实际完成的工作** |
|---|---|
| 待读 | 仅收集入口，尚未检查内容，不能作为已经核实的依据 |
| 略读 | 浏览目录、概览和重点段落，用于判断范围与资料用途 |
| 针对性阅读 | 阅读与问题有关的章节、接口或代码路径，记录实际覆盖位置 |
| 深入阅读 | 检查相关上下文、条件、分支及关联证据，能够说明机制和边界 |

“已总结”可另外记录，表示已经产出笔记，不表示读完全文或运行过代码。阅读范围应具体到章节或路径。不要把工具成功抽取全文当成阅读全文。

独立来源索引中的正式收录条目应写清“一句话价值”：这份资料在本课题中独特地解决了什么问题。可按需增加价值类型，如概念入门、设计依据、实现细节、接口约束、评测方法、反例边界和项目经验。不能用“重要资料”“供参考”等占位句替代内容判断。尚未阅读的候选条目明确标为待判断。

支撑核心定义、主要机制、关键比较或重要结论的材料，必须有可独立阅读的资料条目。条目应像文献阅读记录一样，让读者辨认材料、理解主要内容、判断课题价值并继续阅读，不能只有短链接和一句“用于支撑某结论”。原文较短时可压缩条目，但仍保留实际内容和证据边界。辅助材料可简写为完整参考著录及用途，不要求每份接口页写成长篇笔记。

核心材料的阅读条目至少覆盖以下内容，可按资料性质合并字段：

```text
来源与阅读范围：标题、定位、版本，实际阅读的章节或代码路径
问题：这份资料回答什么
内容与机制：概括材料的实际内容，解释参与对象、状态或执行过程
分析与比较：哪些可借鉴，与相关材料有哪些区别或矛盾
证据与局限：区分来源主张、所读实现和实测，保留条件、限制和反例
课题价值：具体支撑哪个问题或章节，为什么需要这份材料
疑问：还缺什么证据，下一步查什么
```

建议阅读顺序按知识依赖和当前问题组织，例如先概念、再机制、再实现和边界。不按发布时间、厂商知名度或资料数量机械排序。

## 四、References 与证据管理
### （一）引用位置与格式
正文中的关键定义、实现细节、版本支持、限制、数字、比较依据和直接引语必须有就近引用。正文引用可使用简短、可辨识的来源名称并直接附链接，文末必须有独立的 References（参考资料）部分。资料较多时另设来源索引，正文末仍应展示主要参考资料的正式题名、责任方及可定位入口，不能只放一个“来源索引”链接。读者应能直接识别主要依据并进入详细阅读条目。

名称优先采用“机构或作者 + 简短主题”、文档简称或已解释的通用缩写，例如“Python asyncio 文档”“Linux 调度器文档”。同一机构的不同资料用主题区分，必要时增加年份或版本。同一来源在全文及索引中保持相同简称，索引保留完整标题。不使用数字编号、R01 等代号或会被渲染为数字的脚注作为来源的展示名称，也不用“来源”“原始文档”“点击这里”等泛称替代可辨识名称。

同一段的多个事实由不同来源支持时，分别引用。不要在一整章末尾放一个链接，让读者猜测它支撑哪些内容。表格可增加“依据”列。各行证据不同时分别标注。

引用必须指向具体文档、章节、代码位置或记录，避免只链接官网首页、搜索结果页或仓库根目录。同一来源反复使用时沿用相同简称，按主张指向实际支撑位置。正文引用与参考条目通过来源简称及链接相互对应。未用于论证的推荐材料单列“延伸阅读”。

引用带章节锚点时，核对页面上确有对应位置。网页能打开只说明页面可访问。原网页没有稳定锚点时，链接到原页面并写明章节名。

### （二）每条来源的最小信息
下列信息可写成表格或条目，不要求固定数据库格式：

| **字段** | **要求** |
|---|---|
| 来源简称 | 简短、可辨识，与正文引用一致。同名时用机构、主题、年份或版本消歧，不强制建立编号字段 |
| 标题与责任方 | 真实标题、作者或机构。未知时明确写未标明 |
| 来源类型 | 文档、源码、标准、产品页、文章、讨论、实测记录等 |
| 定位 | 原始 URL 或本地相对路径，必要的章节、页码、函数或行号 |
| 版本与日期 | 相关软件/文档版本及发布或更新日期。未知不猜，滚动页注明“滚动更新” |
| 访问日期 | 实际查看日期。不能把访问日写成发布日期 |
| 支撑内容与边界 | 用于证明什么，关键条件及未核实部分 |

正式参考目录采用完整题名，按“责任方，题名，资料类型，版本或年份，原始定位”的顺序清楚著录。发布方没有个人署名时使用机构或项目名，不编造作者。网页、标准、源码和产品材料保留各自适用字段，不强行套用论文卷期、DOI 或发表渠道等级。正文中的短引用是定位工具，不能代替正式参考著录。

较短报告可在文末将正式著录和核心阅读条目合在一起，不必另建文件。来源很多时，来源索引维护完整元数据与阅读条目，正文 References 列主要材料的责任方、完整题名和入口。题名及入口可在两处重复，详细版本、阅读记录和文件位置只维护一份，避免反复抄写造成差异。

独立来源索引必须包含分类说明、建议阅读路线、正式参考目录、核心资料阅读条目和必要的待核实事项。总览用于比较资料的研究角色，核心材料按完整题名单独成条，分开呈现元数据、实际内容、分析价值和局限。可以把正文所需的源码文件组合成一条有明确边界的调用链阅读记录，同时保留各文件定位。不要把所有信息压进一个长段落或宽表，也不要以链接数量代替资料分析。资料类型、核验状态、阅读状态与价值类型分别记录：官方文档也可能尚未核实，深入阅读也不等于本地验证。通用资料无需填写 Venue Rank 或用 NR 作为默认状态。实际纳入论文库的论文按研究目录中的对应规范管理。

以下仅为格式示意，不是真实来源或调研结论：

```markdown
功能 X 仅在满足条件 Y 时可用，见 [发布机构 功能 X 限制](<原始 URL 与章节定位>)。

References：
- 发布机构，[文档完整标题](<原始 URL 与章节定位>)，官方技术文档，vX.Y，YYYY-MM-DD。

核心资料阅读条目：
### 文档完整标题
- 责任方与类型：发布机构，官方技术文档
- 版本与日期：vX.Y，更新 YYYY-MM-DD，访问 YYYY-MM-DD
- 原文与阅读范围：[文档完整标题](<原始 URL 与章节定位>)，“功能 X 限制”章节，针对性阅读
- 内容与机制：说明功能 X 的输入、状态变化及条件 Y 如何限制执行
- 分析与课题价值：比较相关方案对条件 Y 的处理，解释它对当前选择的实际影响
- 证据与局限：这里填写原文真实条件和未核实部分，不能用“尚未实测”代替全部局限
```

### （三）版本与时效
- 软件能力、API、系统要求等应对应目标版本。历史实现可以使用，但必须标明历史范围
- 涉及产品迁移、移仓或多客户端时，先核对各资料对应的产品与版本，再分析实现。
- 源码分析优先使用固定 commit 的永久链接，记录文件路径和关键符号。只有 main/latest 时说明无法固定版本的限制
- 发布日期、资料更新日期、访问日期和报告信息截止日分别记录。截止日后的变更不混入既定时间范围。采用时需显式更新范围
- 价格、许可、配额、支持周期等动态信息在用于实际决策前重新核验。报告不能永久保证其有效性
- 同一课题资料版本不一致时，说明哪些结论可共用、哪些只能分别成立，不能拼成一个不存在的统一版本

### （四）证据状态与矛盾处理
使用自然语言或以下标签区分结论性质，无需逐句机械打标签：

| **状态** | **合适的表达** |
|---|---|
| 来源明确陈述 | “官方文档规定……”“厂商宣称……” |
| 实现分析 | “在 commit … 的函数 … 中可以看到……” |
| 本地实测 | “在以下环境与输入下观察到……” |
| 分析推断 | “依据上述机制，推断……。尚缺……验证” |
| 工程建议 | “针对当前约束，建议……。前提是……” |
| 未核实 | “现有资料不足以确认……” |

来源冲突时，先检查版本、平台、术语、默认配置和实验方法，再分别陈述证据及适用范围。无法消解时保留争议，说明是否影响核心结论。不能因为某条来源较新就自动否定旧版本事实。

文档存在某个 API 不证明目标环境可用。Issue 报告失败不证明普遍不支持。一次测试通过不证明长期可靠。关键主张存在不确定性时，应缩小结论范围，而不是用模糊措辞掩盖。

引用原话需明确标注，保留必要上下文。翻译应注明为译文。摘录和截图只保留必要内容，内部敏感信息在共享前脱敏。AI 的整理或推断不能作为独立事实来源。

## 五、分析与报告写作
### （一）通用报告结构
正式对象／机制类调研先明确研究对象、范围和容易混淆的术语，用短总览说明整体关系与主要判断；随后按共同问题逐项讲清各对象是什么、如何工作、代表场景和能力边界，再在共同场景下集中比较，最后归纳共性、关键差异及适用选择，回答开头的问题。证据、实例和图示跟随所解释的内容，局限和未核项放在影响判断的位置。章节按实际问题合并或展开，不机械凑齐标题。纯知识梳理可只回答问题；需要行动建议时再说明下一步。References 保留独立入口，列出主要资料的正式参考著录，关联分类来源索引和核心阅读条目，延伸阅读另列。

正文必须使读者在不逐一打开来源的情况下理解核心论证。不能用“详见链接”代替解释，也不能把多篇来源摘要依次粘贴当作综合分析。

导读先给读者判断所需的短结论，条件和限制就近保留；实验步骤、原始数字和详细方法放到对应正文。表格用于同一口径的快速比较，单元格保留短语或短句；需要整段解释时，改用相邻正文或列表。正文围绕中心问题展开解释、依据和必要限定，较长专题可收束本节判断与边界。

### （二）机制研究如何展开
涉及现有工具、框架或系统的调研，专题分析应优先讲清代表方案在本次问题上实际如何工作，按需说明入口、参与对象、状态保存位置、处理与更新路径，再开展比较、归纳和建议。区分官方文档说明、源码核查与实际测试，未核实的环节明确保留。

对重要机制，按以下链条组织内容：

**问题与场景 → 参与组件 → 对象和状态 → 执行/数据路径 → 异常与完成路径 → 设计取舍 → 适用边界。**

根据课题回答：谁创建和持有状态、谁调用谁、同步或异步如何完成、失败如何传播、跨越哪些进程或权限边界、代价由谁承担。不涉及的维度无需生硬补齐。

分析源码时，说明入口、关键分支和适用配置，避免把函数名称列表当作调用链。区分公开契约、内部实现和分析者模型。公开资料不足的闭源细节明确留白。

### （三）方案比较如何展开
- 先定义共同任务和必须满足的条件，再选择候选方案与比较维度
- 相同列使用相同口径。“原生支持”“插件支持”“需要开发”“未知”“不适用”分别表示，不能把未知写成“不支持”
- 按课题选择功能、接口、部署、兼容、维护、迁移、成本、性能和许可等维度，无需每次全部展开
- 性能数据必须附版本、硬件、输入负载、配置、指标与测试来源。条件不可比时分别陈述，不作直接排名
- 确需评分时说明权重依据和评分尺度。关键未知项不得默认为零分。权重变化会改变推荐时说明这一点
- 推荐必须是“在什么场景和前提下选择什么”。保留现有方案、不引入新工具也应在相关选型中作为候选

### （四）历史与演进如何展开
只有演进能帮助理解当前机制时才写时间线。每个阶段解释原先的限制、引入的变化和留下的代价，并给出日期依据。区分提出、首次发布、稳定支持和本地采用时间。不要把并存方案写成必然替代关系。

### （五）Mermaid 图示与 LaTeX 数学表达
调研应结合文字、图示和数学抽象，从不同侧面展示同一概念。文字说明含义、机制与条件，在此基础上尽量补充图示展示结构、关系和过程，并为可形式化的内容补充数学表达，明确对象、约束与变化规律。相关文字、Mermaid 图示与适用的 LaTeX 公式应围绕同一概念就近组织，使用一致的名称和符号，说明各表达之间的对应关系。图示和公式均保留配套文字解释。大纲和正文都应主动规划这些表达，不设数量指标，不为缺乏合理形式化依据的内容编造公式。

#### 1. Mermaid 图示
本地 Markdown 使用 `mermaid` 代码块保存图示源码，飞书正文使用原生文本绘图组件呈现，并保留可编辑源码。

架构、依赖、调用流程、交互时序、状态转换和方法关系，在文字说明基础上尽量同时提供 Mermaid 图示。并列属性和比较结果可补充表格，真实测量曲线使用绘图工具。综合课题在大纲中注明关键图拟解释的问题，正文将图放在相应机制附近，说明图中各部分与文字概念的对应关系。

图应标明对象、箭头含义和系统边界，注明是来源原图、改绘还是分析示意，并用来源名称链接引用依据。保留可编辑源码，检查语法、中文标签、连线与正文是否一致。交付格式支持时核对实际渲染，只有源码时如实说明尚未验证显示。交付到飞书时按项目的文本绘图要求执行。

先确定每条边表达的真实关系，再选布局。流程与关系图默认自上而下；真实顺序可排成一列，归属、包含、并列属性、可选关系和分支按实际关系表达，不能为竖排新增因果或层级。节点使用简短术语或动作，字段和参数细节放在相邻正文。复杂图可拆图或配表，确需并排比较时按正文阅读宽度采用横向布局。检查每条边的语义及实际显示；只有源码时说明显示尚未验证。

逻辑分层不能自动画成独立进程。数据路径与控制路径不能混成同一种箭头。各对象覆盖深度不同应说明，不能用对称排版暗示研究完整度相同。

#### 2. LaTeX 数学表达
公式统一使用 LaTeX 编写，包括行内公式和独立展示的公式。

涉及输入输出映射、状态更新、约束、复杂度、误差、概率或成本关系时，在文字解释基础上尽量同时用 LaTeX 明确对象与关系，从数学抽象侧面展示同一机制，并说明与文字、图示的对应关系。区分来源公式、等价改写和分析者建立的模型，保留来源定位与成立条件。

首次出现的符号说明含义、取值范围及必要的单位或维度。同一符号保持同义，不同方法先统一可比符号，再说明假设差异。公式旁保留直白解释，不用无依据的数值、权重或形式化掩盖未知。

本地 Markdown 中，行内公式使用 `$...$`，块级公式使用 `$$...$$`。用于飞书的块级公式在 Markdown 源码中保持同一物理行，多行推导使用 `aligned` 环境。飞书正文应呈现为可阅读的公式，代码格式仅用于讲解 LaTeX 写法。交付前检查符号、上下标及必要渲染，具体格式采用实际交付环境的文档规范。

#### 3. 示例与交付检查
命令、配置和代码片段应标明是概念示例、来自文档的示例，还是已在指定环境验证的内容。不能把未经运行的示例称为可直接部署方案。

完成前检查核心概念是否有清楚的文字解释，是否尽量同时提供了相应图示及有依据的数学抽象，并说明各表达之间的对应关系。图示和公式应与正文、证据和适用条件一致。

## 六、验证与实施的边界
资料调研不默认要求安装软件、修改项目、执行测试或部署。机制可通过文档和源码分析说明，但必须如实描述证据方式。任务包含验证时，再实施与关键问题直接相关的最小验证。

实际执行验证时至少记录：

| **项目** | **内容** |
|---|---|
| 问题与假设 | 本次验证想确认或排除什么 |
| 环境 | 相关软硬件、版本、依赖、配置与时间 |
| 方法 | 输入、步骤或脚本、对照和指标口径 |
| 结果 | 真实输出、日志或测量记录，包括失败与异常 |
| 解释与边界 | 结果支持什么，不能推广到什么范围 |

性能或随机性验证还应说明重复次数、波动和聚合方式。必要时区分加载、预热与稳态。没有运行就写“未执行”，没有测得就不能补造数字。

报告完成、验证通过和实施完成是三个不同状态。实施方案按项目已有开发规则执行，调研建议本身不改变《多人协作代码开发规范》中的职责与流程。

## 七、文件组织与持续维护
### （一）按需组织文件
保留现有课题位置和命名习惯。新课题可采用以下结构。已有明确中文名称时，不强制添加英文。

课题采用中英双语名称时，正文和大纲复用完整课题前缀，格式为 `[课题中文名] [课题英文名] 通用调研 General Search.md` 和 `[课题中文名] [课题英文名] 通用调研大纲 General Search Outline.md`。例如目录 `技能 Skills` 下使用 `技能 Skills 通用调研 General Search.md`，与同课题文献调研保持一致，用户指定英文名优先。历史成果按实际迁移范围更新。

```text
[课题名称]/
├─ [课题名称] 通用调研.md
├─ [课题名称] 通用调研大纲.md    # 正式调研先做，短稿可按要求合入正文
├─ 来源索引.md                    # 来源较多时
├─ 检索日志.md                    # 长期、复杂或需交接时
├─ 资料/                         # 实际需要保存的原始材料
└─ 验证/                         # 实际产生的脚本、日志与结果
```

不创建空目录，不强制保存所有网页为 PDF，不要求每个任务配 CSV。现有目录已经使用“工程资料索引”“来源索引”或 Research Log 时直接沿用，不为套模板重命名。

### （二）归档规则
- 在线原始链接是引用入口。需要固定证据、离线阅读或防止关键内容变化时，再保存允许归档的文件或快照
- 附件名称保留可识别标题，按需增加机构、版本或日期。完整原始标题与出处放在索引中
- 同一内容和版本默认保留一份主文件，跨专题用链接关联。不以下载数量衡量成果
- 原始材料与自己的分析分开保存。改绘图、翻译或节选不能伪装成原件
- 对影响结论的固定附件或验证制品，可记录哈希以便核对。普通链接清单不强制计算哈希
- 文档内部优先使用相对路径。含空格的 Markdown 链接使用尖括号包裹路径。移动或重命名时同步检查引用

保存附件后检查真实格式、可读性和内容是否与条目相符，不能把登录页或下载错误页作为正文入库。文件名避免系统禁止字符，缩短名称时在索引保留完整标题。本项目普通资料路径建议控制在 240 个字符以内，较长路径需检查实际阅读与同步工具的兼容性。纳入论文库的 PDF 继续遵守研究规范的专门路径要求。

### （三）既有资料批量整理
批量整理已有资料时，先盘点实际文件、现有索引和失效链接，再生成“旧路径、目标路径和变更原因”映射，检查冲突后执行。证据不足以确定标题或版本时保留原名并标记待核实，不根据相似搜索结果强行改名。

保持稳定的上层目录和有实际用途的跨专题副本。同哈希只能证明字节相同，不能单凭这一点决定删除。不同版本存在有用差异时保留并注明关系。完成后核对文件数量、可读性、变更映射和引用，重复整理不应继续改动已经规范化的名称。

资料整理与内容调研分别验收：文件齐全、索引可用，不代表技术结论已核实。新增检索或下载也不自动属于已有资料整理的范围。涉及论文库的全库处理时使用《论文库全库整理规范》。

### （四）更新规则
发生目标版本升级、关键来源修订、项目约束变化、发现错误或开始实际采用时，复核相关结论。长期维护课题按变化速度约定复核安排，不对所有资料设置相同周期。

更新时记录日期、变更原因、影响章节和结论变化。历史事实可保留并注明适用版本。核心依据失效且无替代来源时，标记受影响结论待复核。链接打不开不等于原结论已被证伪。

## 八、交付要求
交付成果应围绕调研问题形成有依据的回答，让读者能够理解核心机制与结论、追溯参考资料，并明确结论的适用条件。正文、大纲、来源索引和实际附件应保持一致。验收大纲时应提取实际标题树，核对重要子主题是否展开、标题是否逐级从属、节内是否有问题与证据说明，以及正文是否对应覆盖。排版解析通过不能代替结构检查。验收参考部分时，分别检查正文就近引用、文末正式参考目录及核心资料阅读条目，核对读者能否不打开每个外链就理解主要材料讲什么、彼此怎样关联及为何采用。存在外链或索引入口不等于参考部分已经完整。

第一稿应有足够篇幅展开任务范围内的主要分支。按第三章完成证据核对和自查后一次交付正式报告。

## 九、可复用任务指令
> 请按《通用调研规范 General Research Standard》调研“[课题]”，用于[读者/目的]。重点回答[核心问题]，范围为[对象、场景、版本或约束]，资料截止到[日期]。先参考已有相关调研，将产物保存到[目录]。
>
> 写大纲前阅读项目适用的文档规范正文。即使先写本地 Markdown，也从大纲开始应用同一套命名、标题层级和排版要求。正式调研先形成大纲，综合课题按内容从属关系逐步展开章节与子章节，写明实质小节的问题、代表资料或证据及关键待核实内容，再完成对应正文。同级分类口径一致，子节内容属于父节主题。
>
> 以与主张匹配的官方文档、源码、标准及其他可核实资料为依据，解释机制、差异、条件和代价，区分事实、推断、建议与实测。正文使用可辨识的来源简称直接链接、就近引用，不用编号或数字脚注。文末提供独立 References，列出主要资料的责任方、完整题名和可定位入口。核心材料须有内容与机制、分析比较、课题价值和证据局限的阅读条目，记录来源定位、版本、实际阅读范围与访问日期。来源较多时，由来源索引统一维护完整著录和阅读分析，正文参考部分保留主要资料入口；短报告可在文末合并著录与阅读条目。
>
> 保留清楚的文字解释，尽量同时用 Mermaid 图示和适用的 LaTeX 数学抽象说明同一概念，交代各表达的对应关系、符号、条件与依据。交付前按第三章的停止条件核对核心问题和证据缺口，再检查实际标题树、引用、参考目录、核心阅读条目及必要渲染。按需提供比较、检索日志与附件，不强制论文排名、下载 PDF、实施或跑实验。

## 首稿解释深度核对

正式机制或比较报告应让读者能解释关系、选择入口并说清边界。核心术语、必要中英文名称、字段和图节点相互对应，正文说明边代表动作还是关系。用一个代表场景贯通输入、状态变化、可观察结果和完成判据，在相同前提下比较主要路线，并解释会改变选择的限制。图示放在相关正文附近，按真实关系选布局，不为排成竖列虚构因果或层级；复杂图按需拆分，并排比较时核对实际阅读宽度。对大纲已有而正文只有索引式概括的关键问题，补足直接证据及解释，不用篇幅或图表数量代替深度。小型明确查询不强制展开整套报告。
