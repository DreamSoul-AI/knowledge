# Calendar meeting archive

Collect ended meetings hosted by or inviting the current user, retrieve their original records, prepare minutes for each actual meeting type, and upload them to a specified Feishu folder.

## Install
Install the complete `skills/calendar-meeting-archive` directory. The workflow requires an existing lark-cli setup, the relevant Lark calendar, meeting, document, drive and shared skills, and the current user's source and destination permissions. Service integrations are not bundled here.

This skill can run independently. Pass original material, supplements and applicable rules to meeting-minutes when installed or explicitly selected. Use document-sync for delivery when available or selected. Report missing explicitly selected dependencies rather than silently switching versions. Current project templates, archive rules and access restrictions take precedence.

## Use
```text
Use $calendar-meeting-archive to organize this week's ended meetings from my calendar and upload their minutes to this Feishu folder: <destination folder link>.
```
Specify dates, timezone and filters as needed. Without dates, scan today's ended events in the user's timezone. Without a destination, prepare local results and ask for the folder; do not upload to the drive root. Each person uses their own account and destination; access to an inviter's entire calendar is not required.

## Project placement
Provide an external [grouping and requirements profile](placement.md), or supply natural-language additions for confirmed aliases, archive groups, supplements and applicable standards. Existing series-only profiles remain valid. An ad-hoc meeting may have no series and use an explicitly established shared group. Resolve each occurrence’s identity, group, location and applicable rules before preparing content. Unknown ownership or conflicting requirements remain pending only for affected meetings. The profile is read by the agent, not an executable parser; it neither authorizes uploads nor enables scheduling.

For example, combine two confirmed aliases into one series, apply the regular-meeting standard only to its scope, and place confirmed external ad-hoc discussions in a specified shared group. Keep run-specific additions in the current run record rather than silently making permanent rules. Group changes do not change occurrence identity, authorize migrations or regenerate existing minutes.

## Workflow
[Retrieve original sources](sources.md), read the complete available text, then [upload or update](upload.md). Retain raw evidence and provenance long term. The current request or confirmed project configuration determines whether to deliver records, minutes and applicable advice; a minutes-only default must not suppress explicitly requested records. Unrequested originals, audio, video, resumes and other attachments are not added automatically. Verify each artifact type’s actual destination and audience separately rather than treating a minutes folder or its parent as the original-record destination. Keep only an unresolved artifact local while continuing other confirmed deliveries. Apply project-specific rules to interviews and other specialized meetings, including restricted audiences.

Pair and deduplicate each actual meeting and artifact type separately, with its own destination, document identity, receipt and status. Compare actual source and destination content on reruns. A prior completed meeting or uploaded minutes does not establish record delivery: within the authorized scope, deliver only missing records while reusing existing minutes and their successful baselines. Do not expand this into a historical-library backfill. Skip unchanged results, retain human edits, and report conflicts. Return per-meeting status, actual result links and failures. Query timed-out import jobs before considering another creation.

## Cloud drafts from multiple participants
When several cloud documents may cover the same meeting, follow [cloud-draft reconciliation](reconciliation.md). Confirm the actual occurrence, artifact type and approved archive audience/scope. Compare original material to distinguish equivalent duplicates, complementary content, source-resolvable errors and unresolved claims; keep different audiences separate. Preserve the established canonical document identity. Apply only the targeted canonical-document edits or status links in other versions authorized by the current request, retaining other documents, comments and resources. Do not delete, move or create a third document by default. Without the relevant reconciliation or status-link permission, report a proposal and reuse a confirmed canonical artifact; ordinary upload permission does not grant those additional edits. Track relationships in the existing meeting record rather than creating another database. This workflow does not require a sole publisher or guarantee cross-machine atomic deduplication.

## Automation
Manual and scheduled triggers run the same workflow. A user-authorized scheduler supplies scope, timezone, persistent state, confirmed routing and delivery settings. Follow [recurring execution and recovery](recurring.md): catch up missed intervals, revisit pending material, inherit existing artifacts and baselines, and prevent overlapping writes. A daytime trigger must still cover meetings ended since the preceding run. When classification or destination is unclear, retain local material and record the affected delivery as pending without blocking independent meetings. Installation does not create a schedule, record meetings, request sharing or send messages. If a scheduled run discovers multiple drafts without an explicit reconciliation scope in its current configuration, preserve the evidence and report the issue rather than merging, cleaning up variants or switching the canonical artifact. Structural checks do not establish live permissions or a successful scheduled run; verify actual execution separately.

## Local-only runs
Supply existing transcripts and source responses with execution.mode: local_only to prepare the local archive first. When platform reads are prohibited, do not fetch missing material. A local-only run does not require a remote folder or call a transfer workflow. Compare actual local material and artifacts on reruns and preserve human edits.

A meeting series is separate from a project. Historical titles can identify one confirmed series, and one occurrence may discuss several projects. Retain one source record per actual meeting, with project associations by topic. Cloud delivery requires a separately established scope.

## Per-meeting delivery
Report each meeting by series or type and actual date, with separate local preparation and cloud delivery status for each requested record, minutes or advice, plus direct artifact links. If an artifact remains local, identify its location and the missing destination, conflict or other reason. Distinguish creation, update, reuse, local-only and pending work; an aggregate report is supplementary. External rules may require selected meeting types to have a separate section, specific minutes/advice/source links, or copyable drafts. Read those requirements and drafts from the applicable project rules and existing artifacts rather than duplicating templates in this skill. Other meetings still receive individual results. Manual reviews include reused artifacts in the requested scope; scheduled runs follow the confirmed notification policy. A reporting-only change does not regenerate or reupload minutes. Document delivery does not authorize messages to colleagues or message-board publication.
