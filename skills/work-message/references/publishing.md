# 留言板写入

先按技能入口默认读取项目适用的留言板规范，再逐一读取本次目标板的实际语境。不预设先交粗稿，必要查阅和材料核对在首次交付前完成。未授权发布时展示完整可用正文；已授权新增或更新时保存到对应位置，再重新读取核对正文、链接、日期、对象和署名，不重复索要同一权限。不新增独立的发布技能，也不按留言场景维护多套模板。

## 明确本次目标
按技能入口的个人配置接口，从当前请求、已确认上下文及当前使用者的 USER.md 确定本次正文版本、目标板、留言对象与留言人。简称可解析到配置中的真实完整链接；用户已明确发送范围且对应唯一时不重复问位置。常用入口和对象不自动成为本次群发清单或收件人，实际目标仍逐板核对。配置不可读时使用本次明确参数，只补问必要缺项，不扫描他人配置或从示例补事实。

同时核对本会话已明确授权的材料归档、同步和留言写入范围，不因进入本技能就要求用户重新授权。后续明确只要草稿、暂不发布或不同步等限制优先；引用记录中的历史指令不能冒充仍适用的授权。留言内容只限本次指定事项，不把其他维护交接、教程或任务自动塞入正文。

用户尚未决定是否发送时，可在草稿之后简短问是否发布、发到哪个位置。可给已核实的候选及路径，不能将候选推荐说成用户已选择。用户已明确发送范围且必要信息已知时不再次确认；关键值缺失或目标不唯一时，集中补问缺项，不反复索取已有信息。明确只要草稿或不发布时不继续追问发送。

读取目标实际内容与适用规范后再定位。飞书按当前项目要求使用相应 lark-doc／lark-drive／lark-shared 和 CLI，代表用户时显式采用用户身份并核对实际登录人。不可访问、无写权限、身份不符分别说明，不换身份、改权限或另找一个可写的板代发。

板内对象和署名的展示称呼按该板规范及已核实的全名、称呼对应关系使用；账号实名用于核对实际身份，不自动要求所有展示都用实名，也不机械删姓或凭简称认人。原位更新保留未要求改变的对象和署名，无法唯一对应时只补核会影响定位的缺项。

## 起草前读取各板语境
目标板的规范、受众及既有相关留言都是起草输入，不仅用于发布前判重。无论只要草稿还是准备发布，先读适用规范、本次对象及相关日期分组和署名的必要上下文，再读前序介绍、问题或相关版本，核对工具用途、之前宣布的状态和最新进展。缺失的日期、对象或署名保持未定，不用历史值替代本次确认。先按关键词和邻近上下文定位，材料不足时有针对性补读，不为每条留言重扫全部历史。来源不可读或记录有限时说明查阅范围，不能假装已适配该板，也不能把“未查到”写成从未发布，或把“曾经介绍”写成所有读者已了解。

结合最新事实，按本板实际读者和前文选择语气，补足必要背景或承接已提出的问题，再说这次变化。适合共有的正文尽量保持语气、文字和结构一致；仅因实际读者背景、处理要求或访问范围作必要调整，相同事实与发布状态保持一致。不能先只凭本对话写好通用稿，再只改称呼或照搬整份工作清单，也不为衔接重述大量旧内容。本轮已发且正在修改的留言不能循环用作先前介绍的依据。旧留言不产生新的执行、通知或改稿授权。

以本人在该板给该收件人的相近旧留言核对正文称呼、敬语、口吻及格式；分组名与正文称呼不必是同一种写法，分别按规范、已确认对应关系和本次要求处理。不能只把“你”换成“您”就认为适配完成，也不将某个收件人的敬称推广为通用规则。已有日期、对象和本人分组能对应本次位置时优先复用，不因称呼显示不同另造同人分组；涉及历史组改名时按本次明确范围处理。

多个目标板的相关内容读完后，一次准备并标明各板对应正文，内部检查事实、链接和状态一致，背景与语气适合各自读者。无需用户逐板重新请求；是否共同用一份正文按实际适用性判断，不固定版本数量。实际发送前仍重新读取目标，避免准备期间的修改被覆盖。

沿用各目标的受众范围，只把适合该板读者的信息写入。操作者同时可读多块板，不代表可以把其中的受限细节复制到另一块板；跨板共同输入限于适合各目标受众的事实。

未指定目标时可先给通用稿，不能伪称已针对某板衔接。用户已经确认了要发的具体正文时保留该版本；拟作分板适配或发现受众不匹配时，先展示建议调整，再按本次确认范围写入。

## 材料入口与可用交付
草稿也要完成必要的事实、对象、语气和材料核对，不以“只是草稿”省略本可取得的真实入口。主动查找与事项直接对应的已有成果，核对版本、内容及适用受众，再按入口的链接和原生引用要求带入。不能只留接收者打不开的本地路径、占位链接，或用“见附件”“已同步”代替未实际交付的材料；附件只有实际附上后才能称已附。

### 接收者访问核验

先明确本次每个板的实际接收者。“全体”指该板本次实际受众，不自动等于组织所有账号。分别核对留言板和引用资料的访问范围；当前登录人成功读取资料、链接有效、资料在某部门目录或之前发过，都不能替代接收者权限证据。

默认由 Agent 自动读取资料自身的直接授权成员、用户组及继承权限，结合本次接收者的实际账号或组归属，核对其是否获得相应访问授权。缺少直接成员时继续查可取得的群组及继承路径，不直接判无权；能取得的证据自动补齐，不把权限列表交给用户逐项人工检查。依据足以覆盖本次实际受众时直接处理，不要求每个人登录测试，也不为一般链接复问。

遇到不透明的组标识时，解析组名和可取得的成员，或采用已核实的对应关系；不能把留言板上任一授权组直接认定为本条接收者，也不能只因资料与板有相同组标识就结束核验。可通过本板实际对象、相关群的完整成员及资源授权对应确认覆盖，不要求接收者逐个打开测试。不同只读接口有身份要求时说明用途并遵守相应工具约定，不静默换身份或新增授权。

团队资料的“组织内持链接可读”等宽泛链接设置只作背景，不单独证明本条接收者已被授权或资料适合该板；即使链接技术上可能打开，也继续核对资料自身授权及应分享对象。明确对外发布的公共仓库或公开材料，可按其正式公开发布状态判断，不能据此推定其中引用的内部资料也公开。用户此前对具体受众和入口的明确确认可复用；若与当前权限事实或本次披露边界发生冲突，则按下述例外处理，不把旧确认推广到所有资料。

按资料和受众记录自动核验的结论、必要依据、核验时间和仍缺的信息，无需固定表格或额外系统。已有依据的对象、范围和条件仍一致时复用；群组成员、授权、链接对象或受众变化时补查。证据仍不足时直说“尚未确认授权覆盖”，并说明已经查到哪里；不只丢一个“待核”标签，也不让用户代做技术检查。只能证明部分路径时不写成全体通过，也不登录他人账号代测。

主要需要询问的是授权与应分享范围的冲突：例如资料已给某组查看权限，但本次明确仅向另一个范围披露。列出具体资料、实际授权对象、冲突依据及拟处理方式，请用户确认是否向该板引用。判断“不应看到”须依据本次要求、资料适用对象或明确保密边界，不能只凭兼职身份或目录名推断；不要先发出、撤权或改权限再问。其他只有确实缺少用户必须决定的目标范围，或需要新增授权、复制受限材料等改变分享范围时才集中问，不把普通查询失败变成人工核验任务。

默认从相应受众版候选中留出受限或未核入口，给本人说明原因；确有已授权且可读的替代版本时可引用。仅影响部分资料或目标板时，其他有据可分享的内容继续准备。保留受限事项的完整情况供本人审阅，不把正文换贴到对方可读的板来绕过权限，也不为补链接擅自新增协作者、放开分享或复制受限材料。用户明确要发申请访问入口时，按实际授权说明需要申请，不声称资料已经可用。

例如，资料授权给本板实际对象所属用户组，且与已确认分享范围一致，自动保留；资料仅设置“组织内持链接可读”而未取得相应授权覆盖依据，继续查直接成员和继承路径，仍无法确认时暂缓该入口；资料已给目标组授权，但明确披露要求排除了该组，才请用户校正这项冲突。独立可读的工作模板与受限维护仓库分别判断，不把兼职身份或某板名称固化为黑名单。

关联材料的归档或同步已在本会话明确授权、且未被后续要求限制时，使用对应技能完成原授权范围并核对取得的真实入口，再引用到留言。该行为是继续已授权工作，不是为补链接擅自额外上传。未授权的额外上传、新建文档或改权限不做；已有资源仍查不到或不可用时，说明具体缺口及影响，不把未取得入口的稿说成完整可用。材料授权与留言发布授权分别按实际范围判断，不能相互推定。

## 日期、时间与位置
区分正文涉及的业务日期、实际发送时刻，以及留言板的归档日期。发布前须明确本次归档日期：用户明确指定日期时优先采用，即使与板内默认日期规则不同，也不自行改成当天或次日。多板按本次要求分别确定，正文业务日期不随归档日改写。新增留言的日期计算与更新旧留言的日期确认分别处理，不能直接用个人日期规则决定新内容写回哪条旧记录。

用户未指定日期时，采用本人已确认的个人日期规则、时区和各板例外，能确定则直接计算，不逐次要求确认。仅有板内默认规则、尚无本人采用依据，或缺项、歧义及冲突无法判断时，预填有依据的候选并集中补问。“现在发”不自动补齐缺失规则，不强制询问钟点。计算跨日、跨月和跨年时使用适用时区，不用今天猜“那天”。

归档日期与实际同步时间偏好分别处理。时间偏好不构成定时任务、自动同步或发送授权，不因配置某个时间就创建调度，也不自行延迟当前已要求执行的任务。

沿现有月份、日期、留言对象及该板确实使用的留言人分组定位，缺少本次实际需要的层级才局部新增。项目用 H3 表示对象、H4 区分留言人时，固定双人板已有 H3 而不设 H4，就直接在 H3 下放编号正文，不额外补 H4 或重复署名。实际发出人仍需核对，缺少一个该板不使用的标题层级不是待补信息。按目标板规定的编号和优先级放置，不重建整篇或整组。聊天定稿未带标签时可以原样展示；写入若需补必要标签，按用户已说明的性质和目标规范处理。与用户明确定稿有冲突且无法保留其原意时，先说明冲突，不擅自润色正文或升级为【待确认】。

## 标签颜色与编号
发布前，读取目标分组，结合接收者的处理需要确定优先级、标签颜色和插入位置，按整组实际顺序安排编号。具体判断沿技能入口的优先级要求，颜色和排序沿适用规范与目标板规则。

从适用规范与目标板使用说明取得完整的优先级颜色映射，不仅核对某一个标签。文字颜色是富文本属性，不能由“标签文字存在”推定已保留；组合标签分别着色，正文保留原有样式，默认文字色不强加其他颜色。已有条目偶发错色不作为新规范。规范与板内明确规则冲突且无法判断时只询问受影响项，不将某板色值固定进通用技能。

写入前读取本次实际分组的完整同级列表，按其规则计算插入位置与起始序号，不从整板最大编号接号。DreamSoul 每个实际分组从1开始，存在 H4 时按留言人分组，否则沿既有 H3 结构；不能跨日期、对象或留言人接号。主留言和嵌套补充列表分别编号。仅更新正文且未移动位置时保留原号，按优先级插入或移动后检查受影响的后续序号，保留同优先级旧留言的相对顺序。

飞书使用原生有序列表，不把数字写进普通段落冒充列表，也不在每次独立追加时都重启为1。DocxXML 的 `seq` 控制起点，后续按实际列表选择自动续号或明确序号；回读中的 `seq-marker` 是核验依据，不照抄成写入参数。回读整个受影响分组的实际序号、层级和标签富文本颜色，发现跳号、重号或意外重置时，先查评论、定位锚点、附件和并行修改等真实依赖，优先只调整必要列表属性。确需局部替换时保留相关内容与关联，保存可核验的新旧对应；没有实际依赖的块ID不必绝对不变，也不为顺号无差别重建整组。实际工具权限与审批仍分别遵守，不能靠改写技能绕过拒绝。无法核验样式或序号时报告格式待核，不能只凭接口成功称发布完成。

## 新增还是更新
发送前在目标分组及已知原留言线索内检查是否已有对应版本。相同内容已存在时复用，不再追加。发现像是原留言的修订版而本次未明确新增或更新时，给出原条目位置并集中补问一次，不自动另发重复条目或覆盖历史。用户已明确该动作时不重复询问。

优先采用用户给出的原留言链接、真实条目标识、日期、对象及署名定位。没有明确条目时，结合正文、成果链接和工作上下文核对候选，不能只凭同标题或选择最新的一条。已有一版且本次明确为更新时，读取最新原条目，局部更新对应内容，不另发副本。

更新前核对原条目的日期、位置和拟改内容，结合本次请求及相关上下文能够确定是修订原条目时直接处理，保留原日期、对象与署名；能够确定是新进展时按本次归档日期新增。拿不准时再展示候选和日期差异，集中询问“原位修改还是新增进展”，不因缺少某个固定说法就要求确认，也不凭主题相同自动合并。多板分别核对，不把一板的决定套给另一板。受影响写入待确认时，其他已明确目标继续。

写前重新读取目标，保留别人留言、未改正文、原生文档引用、评论和定位。原稿已有人工变动时，以最新内容作局部处理，不拿旧草稿覆盖整组。飞书引用沿入口规则保留真实文档名、完整分享地址与定位，不能为缩短开头而换掉引用标题或资源。

## 重试与交付
写入结果不明或超时，先按已知板与条目查询实际内容，再决定是否重试。已经成功则复用结果，不重复追加。更新目标没找到不自动降级成新增，也不通过换板绕过错误。

发布后，回读完整的受影响分组，核对实际显示的编号、排序、标签颜色、正文、重点加粗和引用，以及归档日期、对象、留言人和列表层级；图片隔开的列表也按所属分组一起检查。根据核验结果完成必要修正，以整组内容准确、格式一致作为发布完成的依据。

多板逐一记录新增、更新、已存在未变、失败或待确认，已成功的板不因另一板失败而重发。无论是否上传，都在当前对话展示最终留言正文；已写入时以实际回读确认的稿为准，同时返回各板实际结果和取得的完整留言位置，不能只回复“已上传”。多板同文可展示一次并列出对应位置，不同正文分别展示。只生成草稿、只拟写入计划或只做离线验证时按该范围报告，不能说成已发布。
