# 从同一总结写给不同读者

以下是合成情境，演示怎样执行现有的受众、优先级和访问核验要求。对象、事项、标签及分享范围都以本次输入为准，不把示例中的安排沿用到下一轮。

## 一、同一成果，不同处理要求

**输入。** 总结记录了 Agent 工作环境模板更新和一项项目内部试验。使用组本周需要采用模板，交流组只需了解变化。内部试验本轮明确不分享。两组都能取得模板下载包，但交流组不能读源码仓库。板上旧留言一直用“Agent 工作环境模板”这个名称。

**不合适的写法。** 两板都写“【知会】Workspace 更新了，相关试验也完成了”，只附源码仓库。

**使用组正文。** 【本周】Agent 工作环境模板更新了，补充了个人配置保护和能力更新入口。请本周按板上已有的模板下载入口更新，保留自己的配置

**交流组正文。** 【知会】Agent 工作环境模板更新了，补充了个人配置保护和能力更新入口，下载包仍在原入口

**这里的区别。** 同一变化可以共用表述，是否需要行动决定标签和必要细节。源码不可读不等于模板不可用，应选择已核实的交付入口。实际交付时带上该入口的真实链接，示例句子不代替材料核验。

## 二、采用能力，把调用关系说清楚

**输入。** 使用者要知道怎样更新已有能力，另一个板只需知会进展。正式入口已经发布。旧留言用“Agent 工作环境模板”介绍面向使用者的成果，用技能名说明调用方式。

**不合适的写法。** “【知会】Workspace 默认接上了这一步，已经完成若干轮校验。”读者不知道“这一步”是什么，也不知道如何使用。

**采用能力的写法。** 【有空】[knowledge](https://github.com/DreamSoul-AI/knowledge) 已提供能力更新 **[knowledge-update](https://github.com/DreamSoul-AI/knowledge/blob/main/skills/knowledge-update/SKILL.md)**，可以单独检查或更新已采用的技能和工具。工作区更新 [workspace-update](https://github.com/DreamSoul-AI/knowledge/blob/main/skills/workspace-update/SKILL.md) 默认调用它，更新时保留有效的本地定制

**只知会进展的写法。** 【知会】[knowledge](https://github.com/DreamSoul-AI/knowledge) 补齐了已采用能力的更新入口，工作区更新会调用 **[knowledge-update](https://github.com/DreamSoul-AI/knowledge/blob/main/skills/knowledge-update/SKILL.md)**，保留有效的本地定制

**这里的区别。** 采用能力时说明谁调用谁、怎样进入及影响使用的条件。只知会进展时保留关键变化，不搬入测试经过。示例没有确定的处理期限，因此采用项用【有空】；本次另有明确安排时按实际期限处理。

## 三、权限证据不全，先补查再决定

**输入。** 本次希望向学习组分享一份使用经验。作者可以读，学习组可以读留言板，但资料的授权成员尚未查全。

**不合适的处理。** 直接从学习组正文删掉该项，理由写“兼职不能看”；或只凭“组织内持链接可读”宣布核验通过。

**补查后有依据。** 查询确认资料继承的授权组包含本次接收者，且与本次分享范围一致。保留这项和原始分享链接，按板上惯用名称写出它帮助读者解决什么问题。把核验依据留在准备记录，不把权限查询过程塞进留言正文。

**补查仍有缺口。** 具体记录缺少哪组成员或哪层继承信息，暂缓尚未证实的入口，保留本次希望分享该项的选择，继续完成其他正文。不把“未核实”改写为“不适合分享”。若实际授权与明确保密边界冲突，才将这项具体决定交给用户。

**后续纠正。** 用户补充“这次两组都只知会，不要求采用”，就更新处理要求与措辞，保留已经核实、仍适用的事实和链接。若纠正了一个漏项，还应检查同类遗漏，但不把这个例子变成永久的必发项目。
