# knowledge 文档规范

本规范说明 knowledge 仓库怎样介绍、说明和维护其技能、工具及定时任务定义。读者应能从首页找到合适能力，理解输入、实际作用和使用条件，再沿准确入口安装或调用；维护者能够据同一份说明核对名称、双语内容及分发包。

它是在既有文档要求上补充本仓的具体分工，不替代各技能的专项规范。研发协作、分支、提交、发布和个人配置来源仍由 [REPO.md](../REPO.md)及其关联约定管理，不在这里另设一套流程。本规范本身也不产生安装、发布或业务操作授权。

## 文档入口和读者

首页面向寻找能力的使用者，先说明仓库提供什么，再按实际用途组织技能、工具和定时任务入口。条目保留名称、短用途和可直接打开的说明；较长机制、完整命令和验证经过放回相应文档，不把首页扩成每个能力的完整手册。

技能、独立工具和定时任务定义分别说明，不把工具目录写成已经安装的技能，也不把定时任务定义写成已经部署运行。外部维护的能力可按用途出现在首页，同时保留其实际维护仓库、安装入口及访问条件。

`SKILL.md` 负责让 Agent 知道何时使用能力、怎样执行及需要读取哪些依赖。`references/` 承载按需读取的细节和使用说明，工具文档说明其真实运行入口，定时任务文档说明提示词、配置和部署条件。内容按实际需要归位，不为了统一格式给每个能力增加同样的文件。

研发文档从 [docs 导航](README.md)定位。本仓能力如何使用，与维护这些能力时发生了什么分别组织：当前说明保留有效用法，设计变化和验证经过沿既有开发、运行记录追溯。历史报告不直接当作当前能力或最新验证。

## 能力归纳和收录

knowledge 的收录应形成有清楚用途和职责的能力积累。先看已有能力及同类经验，归纳它们解决的共同问题，再判断是补充原说明、完善已有技能、组合现有能力，还是值得独立维护。技能数量和收录量本身不代表价值，不把每个案例、临时脚本、新发现或未经验证的想法都直接包装成新技能。

学习和整理时，要辨明共性与特性。共性说明哪些问题、做法和条件可以复用；特性保留场景、平台、任务或证据中影响理解和使用的差异。根据材料和实际用途把握抽象程度，不为归纳强行合并，也不为统一入口删去有意义的细节。尚不能归纳的内容可以先作为案例或待验证想法保留，不急于推广成通用规则。

例如，对话回顾和归档可以复用公开记录读取，但回顾负责解释讨论与决定，归档负责保真保存原文；共同依赖可以抽出，职责差异继续保留。平台的原始记录格式和侧栏工具属于具体适配，也应说明实际条件，不能因改成通用名称就抹去这些特性。

新增独立能力时，说明它带来的用途或职责、与已有能力的关系及已取得的依据，让读者能够判断何时选择它。项目案例和实验材料按各自位置积累，工具及定时任务按实际角色组织；外部能力的发现不自动等于本仓采用。相关资料可以相互引用，不把首页或技能目录变成不经取舍的入口堆积。

## 中英文名称

中文名称说明用途，英文正式标识沿用现有的小写字母、数字和连字符。两者并列时留一个空格，采用“中文用途名 英文标识”，如“工作总结 work-summary”“通用调研 general-search”。英文标识不另写为 `Work Summary` 或 `General Search`。

英文首页使用正式英文标识，中文首页、技能标题和已有界面名称使用对应的中文用途名及英文标识。工具入口采用同样的对应方式，不另造中文目录或重复包。

同一能力只保留一个正式调用名；同组能力采用一致前缀。对话能力统一使用 `conversation-management`、`conversation-review`、`conversation-archive`、`conversation-resume`、`conversation-refresh`，不按不同平台再维护同义的活跃技能。产品名用于实际支持、来源格式和工具依赖说明，不代替通用能力名称。

| **位置** | **写法示例** |
| --- | --- |
| 英文首页 | general-search |
| 中文首页、技能标题 | 通用调研 general-search |
| 已有界面名称 | 对话回顾 conversation-review |
| 中文工具入口 | 多仓库共享资源接入 shared-repository-resources |

目录、`SKILL.md` 的 `name`、`$skill-name` 调用方式和链接指向共同标识同一能力。整理显示名称时保留这些稳定入口；正式改名才连同迁移和兼容处理。修改已有 `interface.display_name` 时保留其他默认提示词、策略和依赖字段，没有元数据文件的技能不为补名字建立空壳。

正文中的 GitHub、Grok Bot CLI、Python、Figma、Codex 等产品或技术名保留原有写法，不全文替换成小写连字符。外部维护的 [figma-design](https://github.com/DreamSoul-AI/figma/blob/main/src/figma-design/SKILL.md)和[browser-test](https://github.com/DreamSoul-AI/testing-system/blob/main/skills/browser-test/SKILL.md)沿用上游标识，本仓可以补中文用途说明。历史记录保留当时名称和版本，旧链接迁移提示不当作另一个正式技能。

定时任务按用途命名，频率由部署配置选择，不把频率当作能力边界。已有入口需要改名时，按明确范围核对引用和兼容，不仅依据这条原则自动改目录、任务名称或调度。

## 使用说明写清什么

先让读者知道能力做什么、适合什么请求、需要哪些输入，以及结果会在哪里。会影响调用的环境、依赖、账号或资源权限放在对应操作附近。实际行为、使用者需要填写的配置和示例占位值分清，不让读者从一段可复制命令里猜缺少什么。

例如，已有公开 Markdown 或文本可用于讨论回顾；Codex JSONL 的原始记录解析、原生耗时和保真归档则依赖对应适配。项目与侧栏操作、向其他对话发恢复或刷新请求，也取决于当前平台工具和已有授权。文档应分别说明通用目的与目前实际支持，不能将名称通用化等同于所有平台均已实现。

例如，document-sync 的说明应区分“脚本只作本地状态判断”和“Agent 调用飞书工具执行传输”。不能因为包含状态脚本，就把它介绍成独立运行的同步服务；也不能把身份核验通过写成所有文档都具备读写权限。

操作示例保留开始使用所需的路径关系、工作目录和必要条件，安装、联网、写入或清理等影响按实际操作说明。共用包不写死使用者的账号、个人目录或真实凭据，项目和个人要求沿现有配置入口接入。

说明深度按能力和读者需要决定。简单用法给能开始使用的例子，复杂机制沿代表场景解释输入、处理和结果，再链接细节。遵守适用的专项规范，不把本仓的首页写法或统一小节模板强加给调研、会议和研究计划等业务成果。

## 双语和分发内容

中英文入口维护同一能力的用途、名称、调用路径、依赖和状态。表达可以按语言习惯调整，但影响使用的前置条件、限制和操作方向应一致。只改名称时不顺手改写业务流程，使用方式变化时检查两种语言对应说明。

更新以完整必要分发内容为单位：`SKILL.md`、已有元数据、引用、脚本和实际依赖一起核对。首页或文档中的安装说明与实际目录对应，不能只复制单个指令文件便称完整安装。

若已有 ZIP 等下载包，名称、标题和元数据也须与目录版对应。例如目录版已改为“对话回顾 conversation-review”，下载包不能仍保留另一套界面名。局部改动只同步受影响成员，核对其他内容，长期依赖和许可证继续保留；验证材料、缓存及个人配置不因此进入共用包。

外部仓库维护的技能只保留必要发现和安装入口，不在 knowledge 另复制一份长期手册或实现。个人技能与通用能力的来源及分支按 REPO 约定区分，文档不将个人设置说成所有使用者的默认值。

## 链接、图示和结果状态

仓内说明链接实际相对路径，跨仓库资料指向其真实来源。移动、改名或修改入口时检查相关导航和调用引用。私有仓库或内部资料链接说明访问条件，不因维护者能打开就推定读者也可访问。

复杂关系按适用规范使用可编辑 Mermaid，节点保留关键对象和关系，细节由相邻正文解释。保留必要图源和长期资源。Markdown 解析通过、目标平台渲染及真实运行分别核对，没有看过实际渲染就不声称显示已验证。

介绍结果时分清本地修改、格式检查、隔离验证、真实平台操作、安装和发布。举例说明实际覆盖的条件，不把一次成功推成所有环境可用。与用法无关的详细测试过程放运行记录，当前入口保留影响采用的结论及限制。

## 文档维护和交付核对

修改前读当前文件，保留人工及并行改动。围绕变化检查首页、包入口、双语说明和实际依赖，不能只改一处名称就认为全部入口已一致。没有实质变化的文件不为形式重写。

从读者的一次真实使用顺序核对：能否在首页选到能力、读懂条件、找到安装和调用入口、理解结果及未完成部分。再检查名称、链接、元数据、编码、换行与必要分发包。纯文案和元数据调整不需重跑无关业务实验，实际行为变化另按本仓规则验证。
