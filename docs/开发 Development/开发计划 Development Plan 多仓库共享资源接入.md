# 多仓库共享资源接入开发计划

## 目标和范围

主要让研发中的多个仓库共享数据、模型及权重，集中管理并按需复用运行产物，通过目录符号链接保留各仓库所需入口。产物可按项目隔离，需共享的部分则明确配置。配置和操作流程应能在另一台设备、另一组仓库或另一类共享资源上复用。资源本身是否已存在、链接权限和程序是否采用该路径，均在实际环境核对。

本机资源接入是当前范围。符号链接引用当前设备可访问的资源，不负责把文件传到另一台设备，也不自动提供版本同步或多方写入协调。研究文档、项目代码及私有配置继续按各自用途管理。

## 输入和可调整部分

- **仓库范围**：明确选择的仓库路径和稳定标识，不绑定 GitHub、组织名、个人盘符或某一层目录扫描方式
- **资源位置**：使用者指定的共享根或已有资源目录，可位于与仓库不同的位置
- **映射关系**：明确共享资源到各仓库入口的对应。数据、模型、运行产物是现有案例，配置应允许素材、测试夹具等其他适合共享的资源，也允许各仓库只接入其中一部分
- **操作范围**：区分读取和预览、创建入口、迁移实体内容。迁移前另核对数据归属、使用方、冲突及恢复依据，个人配置不随技能分发

当前通用工具使用 JSON `resources` 和 `repositories` 接收明确资源及逐仓库映射，资源名、类别、目录与仓内入口均可配置。不同仓库同名时，先确认资源是否应共用；按仓库隔离的资源使用不冲突的稳定标识。

本轮命名调整的推荐配置使用仓库外的 `shared/` 资源根、仓内 `.shared/<资源名>` 入口。`.shared/` 本身是普通目录，资源子入口是符号链接。工具仍接受旧 `.local/` 和任意自定义配置；项目采用新命名时，应将相应共享入口和使用路径改为 `.shared/`，不把长期保留两套入口作为完成标准。资源目标和其他用途的 `.local/` 不变，artifacts 仍按项目隔离或显式共享。

## 当前可复用部分和差距

现有 workspace 脚本支持显式传入仓库根、共享根和所选仓库，默认预览，检查实体入口及 Git 跟踪冲突，复用正确链接，补齐 Git 忽略，并支持所测中断后的重跑。来源与真实验证见 [运行记录](<../运行记录 Run Record/2026-11-15 定时任务与共享资源验证.md>)。

旧 workspace 初始化器固定 data、models、artifacts，保留其现有行为。本轮通用实现移到 knowledge 的 [共享资源工具](../../tools/shared-repository-resources/README_zh.md)，不依赖旧默认布局。损坏链接及入口父目录的 Windows 目录联接点已有拦截，实体迁移、其他平台和并发修改仍不在已验证能力内。

本轮分别用研究资料和设计素材两组 Windows 临时仓库验证任意资源映射、重跑和冲突，另验证通用工具换位置与可选研发配置。其他操作系统和实际项目消费者仍需对应验证。机制、职责及代码结构分别见本目录对应调研与设计，执行证据见 [本轮运行记录](<../运行记录 Run Record/2026-11-15 可配置共享资源接入验证.md>)。

## Workspace 接入建议

把共享资源检查放在新建、克隆后首次接入研发仓库时，也在项目首次引入已有数据、模型或其他共享目录时触发。研发 AGENTS 模板放一条执行入口，Workspace 使用教程维护完整步骤，项目 REPO.md 只记录实际采用的入口和使用方。

**研发模板拟文**：新建或首次接入研发仓库时，检查项目是否需要复用现有目录资源。需要复用时，读取本机 USER.md 已配置的共享根及项目已有映射，找到实际资源和使用方，主动用 knowledge 的 [共享资源接入工具](../../tools/shared-repository-resources/README_zh.md) 预览本仓库的映射。数据和模型按资源名存放，例如 `data/<数据集名>/`、`models/<模型名>/`，目录中省略课题名层级。已有业务路径优先沿用。映射、权限和范围均明确时，按当前任务授权应用并核对实际读取入口。没有共享需求时跳过；缺少资源或遇到占用时，列出具体缺口或冲突。

2026年11月22日已只读核对 Workspace main：研发模板和[接入示例](https://github.com/DreamSoul-AI/workspace/blob/main/templates/software-engineering/examples/shared-resources/README.md)已包含上述主动触发点，以及实际下载、缓存和读取路径的核对，不再沿用此前“尚未提交或同步”的状态。现有 REPO 模板的可选字段可供采用项目记录实际入口。

本轮已启动独立 Agent 实测两个首次接入样例：一个复用已有数据和模型，一个不需要共享。后者正确跳过；前者主动调用了工具，但权限失败后换用 Junction，导致原工具不能重跑复用，未通过完整接入验收。补充调用方的权限失败处理和同工具复验约定后，在新样例复测：工具重试成功，实际符号链接可复用，项目程序读入正确输入。结果只覆盖所测 Windows/CLI 条件，真实业务项目与其他设备仍待按具体范围核对。上述约定维护在[工具说明](../../tools/shared-repository-resources/README_zh.md)，原始验证材料留本地；未增加独立 Skill。

## 实施顺序和验收

本轮工具交付包含推荐命名、双语说明、配置示例和隔离验证，通用实现不变。Workspace 负责共用模板及真实项目的入口改名、配置、消费者、Git 忽略和 AGENTS/REPO 适配。工具发布不代表真实项目已完成迁移；临时双入口只用于迁移过渡，最终需验证新路径的实际使用。历史证据中的旧路径保留原义。具体边界见[已有入口调整](../../tools/shared-repository-resources/README_zh.md#已有入口调整)，本轮验证见[运行记录](<../运行记录 Run Record/2026-11-23 共享资源入口命名验证.md>)。

1. **验证实际项目采用**。选择用户明确范围内的项目，先只预览配置，核对入口类型、消费者和实际资源。已有真实数据迁移另定范围，不用测试配置操作生产目录
2. **按需要补其他环境**。换设备时核对实际路径和权限，其他操作系统执行同一隔离用例，记录不支持的能力。Windows 两种合成布局通过不替代其他设备证据
3. **接续真实项目验证**。在上述隔离建仓演练基础上，按实际采用范围核对项目消费者和执行权限。已采用项目在现有说明或 REPO.md 记录使用方和配置入口，个人路径留在本地；不把有限演练视为所有项目均已采用
4. **再评估迁移和封装**。确有实体迁移需求时，明确映射、使用方、Git 跟踪、完整性和恢复方式后再实现。先在隔离样例验证，生产迁移按明确范围执行。技能层负责判断和编排，工具承担文件操作，依据实际复用价值决定是否新增独立 Skill

换设备验证至少检查实际路径、已有资源、链接权限及消费者，不把更换根目录的同机测试写成另一操作系统已通过。共享目录涉及环境二进制、权限或同时写入时，先核对适用条件，避免将文件可访问等同于运行环境兼容。

## 交付标准

用显式输入接入多仓库，保留实际映射和冲突说明，验证链接目标、所需内容及项目消费者，重复执行和受控中断接续有证据。配置示例不含个人路径或身份，旧工具的默认结构作为可选案例保留，未验证的平台和迁移场景如实注明。
